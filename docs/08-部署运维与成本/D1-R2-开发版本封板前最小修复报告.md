## A. 登记结果核实：不再从"待登记列表里没有"推断"已登记"

**问题。** Q3-R1 在请求结果不确定时重新读取待登记列表，项目不在列表中就显示"已登记（服务端确认）"并关闭表单。但项目从列表消失还可能是授权被撤销、账号被停用或范围变化。修复前的页面在"提交期间授权被撤销 → 403"时显示"FP-1 已登记（服务端确认）。为避免重复提交，表单已关闭。"，证据 `docs/04-前端与可视化/evidence/q3-inventory/8-before-revoked-shows-success.png`。另外，通用 503 等错误文案声称"未做任何修改"，响应本身并不能证明这一点。

**修复。** 文件 `apps/web-console/src/cloud/inventory-registration.ts` 与 `PendingInventoryProjects.vue`，复用已有的 `GET /api/v1/projects`，没有新增 API。

只有 400、422 和"行政区数据不可用"的 503 这三类响应，服务端是在任何数据库写入之前作答的，可以直接显示"未被受理"。其余情况一律进入核实：401、403、404、409、通用 503、其他状态码，以及网络失败或超时。

核实时，只有在调用者有权读取的 Inventory 中找到该项目、并且它带有 lifecycle，才算正面证据。

- 行政区和生命周期与本次提交一致：显示"已登记（服务端确认）"。
- 内容不一致：显示"已由其他操作登记"，列出服务端当前保存的行政区，并说明本次表单内容没有被应用。
- 项目不存在、读取失败或返回空：显示"结果待核实"，保留草稿。

核实期间提交按钮禁用。所有错误文案都不再出现"未做任何修改"。

**浏览器反证。** `tests/e2e/premium/inventory-registration.spec.ts` 使用有状态的模拟 API。

## B. 首次升级的恢复提示

**问题。** D1 的提示是"git checkout <旧SHA> && … && dev-upgrade.mjs rollback"。经 `git cat-file -e` 核实，服务器当前运行的 `7565ee4` 不含 `deploy/scripts/dev-upgrade.mjs`，也不含 `deploy/compose/docker-compose.crane-dev.yml`，所以这条指令不可执行。而且首次升级是 schema 4→12，本来就不允许回退镜像。

**修复。**

- `deploy/scripts/dev-upgrade.mjs` 新增 `recoveryGuidance`，冒烟失败时按三种情况给出提示：
  - 含迁移：STOP，禁止回退镜像，只能按经过验证的人工步骤从备份恢复，并需 OWNER 批准；
  - 旧 SHA 不含本工具：STOP，没有自动回滚，需在单独保留的控制目录中人工恢复；
  - 旧 SHA 自带本工具且未迁移：可以在旧 SHA 的干净 checkout 中执行 `rollback`。
- `rollback` 本身未改，schema 不一致时仍然 STOP。
- 本轮没有编写任何自动恢复脚本。
- D1 报告 §4 第 5 步已更正，新增 §4.1 恢复说明和 §7.2 遗留表。

**最小回归检查。** `tests/contract/dev-release.test.mjs` 覆盖以下几点：

- 首次升级失败时的提示不含 `git checkout` 和 `dev-upgrade.mjs rollback`；
- 4→12 时提示以"STOP: … Do NOT roll back images"开头；
- 旧 SHA 自带工具时，只要有迁移仍然 STOP；
- `rollback` 在 schema 前移时 STOP，且不执行 `up`（原有断言保留）。

变异验证：把迁移分支改成恒假，或把 `rollback` 的 schema 检查改成恒假，测试都会失败（10 通过、1 失败）；还原后 11/11 通过。
