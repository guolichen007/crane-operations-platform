## 3. 构建流程与镜像管理

1. OWNER 对一个**已九项全绿**的完整 SHA 打注释标签 `dev/crane-<名称>` 并推送。标签不触发 `ci.yml`，`production-release` 只在 main 推送时运行。
2. `dev-candidate.yml`：只读 API 核对同 SHA 最新绿色 CI 的九项作业 → `dev-candidate.mjs` 复用 `release-lib.mjs`：`SOURCE_SHA` 构建 → 校验 `org.opencontainers.image.revision` → Trivy HIGH/CRITICAL 为 0 → CycloneDX SBOM → 推送 `…/dev/<name>:<完整SHA>` → 读取注册表 digest。
3. 产物 `crane-dev-candidate-<sha>`（90 天）：`dev-manifest.json`（源码 SHA、CI run、两个 digest、SBOM 哈希、迁移最高版本、Go/Node/PG/Keycloak/Mosquitto 版本）、SBOM、Trivy JSON。
4. 部署依据只用 `image@sha256`；不用 latest、可变标签或生产命名空间。`release-check` 拒绝把开发清单当生产发布、也拒绝把生产镜像名放进开发清单。

**构建成功 ≠ 部署获批。** 清单固定写入 `deployment: NOT_APPROVED`；工作流不含 SSH、compose 或 dev-upgrade。

## 4. 现有 Crane 环境的开发版本切换

前置条件（每次都要）：OWNER 书面批准本次 SHA 与 digest；服务器仓库 checkout 到候选 SHA 且工作区干净；私有 env 文件 0600，`CRANE_CLOUD_IMAGE`/`CRANE_WEB_IMAGE` 改为候选 digest，并保存上一份 env；shell 中不得设置 `CRANE_*_IMAGE`/`APP_ENV`/`CRANE_DEPLOYMENT_ENVIRONMENT`；DockerRootDir 与备份盘空间检查通过。

```bash
# 0) 仍在旧版本 checkout 时：固定上一版有效 digest 与 schema（只读，生成 0600 记录，不覆盖已有文件）
node deploy/scripts/dev-upgrade.mjs record /srv/u-dao/secrets/crane-ops/crane.env /srv/u-dao/releases/crane-prev-<旧SHA>.json
# 1) 若候选含新迁移：用旧版本做备份（backup.py 只做快照，不改库）
python3 deploy/scripts/backup.py backup --env-file <env> --source-sha <旧SHA>
# 2) 切到候选 SHA，env 改为候选 digest，然后只读计划
git checkout <候选SHA>
node deploy/scripts/dev-upgrade.mjs plan dev-manifest.json <env> <prev.json>
# 3) 变更窗口（OWNER 批准）：
node deploy/scripts/dev-upgrade.mjs apply dev-manifest.json <env> <prev.json> [/srv/u-dao/backups/crane-ops/crane-backup-…]
# 4) 浏览器人工冒烟：登录→首页 KPI→资产中心→退出；记录结果
# 5) 失败时：按 §4.1 处理，不要照搬"切回旧 SHA 再 rollback"
```

`plan` 只读，逐项检查：候选清单（开发命名空间、SHA、SBOM 哈希）、checkout 与 SHA 一致、resolved compose 通过 `validateDevelopment`、env 中两个 digest 等于候选、postgres/keycloak/mosquitto 镜像等于候选清单固定的上游（不同即 STOP：共享服务不在本次范围）、正在运行的 digest 等于固定记录、数据库 schema 未变、候选迁移版本不低于当前。

`apply` 只对 `cloud-api web-console` 执行 `pull` 与 `up -d --no-build --no-deps --wait`，不会重建 postgres、keycloak、mosquitto，不碰 Ingress 和其他平台。若涉及迁移：必须给出完整备份集（校验和、来源为上一版 SHA、schema 等于当前、6 小时内），并且 `backup.py drill` 在隔离临时库中恢复成功，否则 STOP，不升级。升级后核对两容器的镜像与 revision 等于候选、schema 等于目标，再跑自动冒烟（首页 200、OIDC issuer 精确、`/api/v1/projects` 未登录 401、`/health` 与 `/admin/` 不公开）。

停止条件与退出码：`1` 拒绝；`2` STOP（运行镜像偏离记录、schema 意外变化、候选 schema 更旧、共享服务漂移、迁移缺备份或演练失败、回滚时 schema 已前移）；`3` 冒烟失败，输出 §4.1 中适用的恢复提示。回滚若发现 schema 已不同于上一版运行时的版本，直接 STOP，不盲目回退旧镜像；是否从备份恢复由 OWNER 另行决定。

### 4.1 失败后的恢复（D1-R2 更正）

D1 原文第 5 步写的是"git checkout <旧SHA>，恢复上一份 env，然后 `dev-upgrade.mjs rollback`"。这条指令对首次升级不可执行：服务器当前运行的 `7565ee4`（main 系）不含 `deploy/scripts/dev-upgrade.mjs`，也不含 `deploy/compose/docker-compose.crane-dev.yml`（已用 `git cat-file -e 7565ee4:<path>` 核实），切回旧 SHA 后根本没有这个工具；`rollback` 又要求 checkout 等于旧 SHA，在候选 checkout 里也跑不了。同理，第 0 步"仍在旧版本 checkout 时 record"在首次升级时也必须改为：从单独保留的候选 SHA 控制目录执行只读的 `record`（它不检查 checkout，不改任何东西）。`7565ee4` 含 `backup.py`，第 1 步可以照做。

现在 `apply` 冒烟失败时按下面三种情况给出提示（`recoveryGuidance`，契约测试覆盖），不再输出不可执行的命令：

| 情况 | 工具输出 | 要做的事 |
|---|---|---|
| 本次含迁移（首次升级即 schema 4→12） | `STOP: schema moved 4->12. Do NOT roll back images …` | 禁止回退镜像：旧二进制在新 schema 上的兼容性没有任何证明。只能用升级前那份已通过隔离演练的备份集，按经过验证的人工恢复步骤恢复两个数据库，再恢复上一份 env 拉起旧 digest，全程 OWNER 批准 |
| 不含迁移，但旧 SHA 不含本工具（如 `7565ee4`） | `STOP: the previous revision … does not contain dev-upgrade.mjs …` | 没有自动回滚。在单独保留的控制目录（候选 SHA）中：恢复上一份 env，只对 cloud-api、web-console 执行 `--no-deps` 重建到记录中的旧 digest，然后人工冒烟；OWNER 批准 |
| 不含迁移，且旧 SHA 自带本工具 | `Rollback: in a clean checkout of <旧SHA> …` | 在旧 SHA 的干净 checkout 中恢复上一份 env，执行 `dev-upgrade.mjs rollback`；它在 schema 已前移时仍然 STOP |

"单独保留的控制目录"指部署前在服务器上另行保存的一份候选 SHA checkout（与运行目录分开，切换和恢复期间不动），恢复时用它里面的工具和 compose 文件，而不是指望旧 SHA 里有新工具。

本轮没有编写自动恢复脚本：`backup.py` 只有 `backup` 与 `drill`（在隔离临时库中恢复后删除），仓库里没有对生产库执行恢复的命令，相应的人工恢复手册尚未写成、也未实际演练，列为 P1 遗留（见 §7.2）。`rollback` 在 schema 不一致时 STOP、迁移失败提示不含 `git checkout`/`rollback`，这两条由 `tests/contract/dev-release.test.mjs` 锁定；人为把任一条件改成恒假，测试即失败（已做变异验证）。

**uatdata 的 fail-closed 规则**：

1. 不能只凭传入的 URL 或参数执行：必须同时满足三项服务端事实。
   - 所连库名为 `crane_app`。
   - 集群 `system_identifier` 与事先只读记录的值一致。
   - 库级设置 `crane.deployment_environment=crane-dev` 存在。这项从系统目录 `pg_db_role_setting` 读取，会话级 `SET` 或 `PGOPTIONS` 伪造无效。它由 DBA 经 OWNER 批准设置，正式上线时删除，此后工具永久拒绝。
2. issuer 必须精确为 crane realm，且库中没有其他 issuer 的账号。
3. 清理只删工具自己的精确 ID，不再使用 `LIKE`。名字恰好以 `UAT-`/`uat-` 开头的真实项目或账号不受影响。
4. 写事务内先做所有权检查。出现以下任一情况，整个操作拒绝，一行不删：
   - 真实账号被授予 UAT 项目权限，或 UAT 账号被授予非 UAT 项目权限；
   - UAT 项目里出现手工创建的资产、位置或目录数据；
   - 项目标记被改动，或 UAT 账号换绑了其他 issuer。
5. `audit_logs` 永不删除。本轮未执行任何 seed/refresh/cleanup。

### 7.1 D1-R1 只读核查：dev-upgrade 与 backup.py 接口（2026-11-10）

结论：未发现确定性 P0，本轮不改代码。以下是需要在首次部署前处理的事项。

| 级别 | 发现 | 下一阶段处理 |
| --- | --- | --- |
| P1 | **首次部署必然涉及迁移，且跨度很大**：main `29c6ec9` 只有 00001–00004 四个迁移，本分支到 00012，新增 8 个迁移。若服务器当前运行的是 main 版本，`plan` 会报 `migration=YES`，`apply` 会强制要求备份并在隔离库演练恢复，逻辑正确。但 4→12 的旧版兼容性无法证明，失败后 `rollback` 会按设计 STOP，只能从备份恢复 | 首次部署前确认服务器实际 schema；准备"从备份恢复"手册并经 OWNER 批准；备份必须由旧版本 checkout 执行 |
| P1 | **首次 `record` 可能无法执行**：`running()` 要求两个容器运行 `image@sha256` 引用，且镜像带 40 位 revision 标签。如果服务器当前镜像是本地构建或只有标签，`record` 会 STOP，无法生成旧版本记录，`plan`/`apply` 也就无法进行。这是 fail-closed，不是漏洞，但会阻塞首次部署 | 由服务器 CC 只读确认当前镜像引用和标签；若不满足，需另行决定首次基线的人工固定方式（不在本轮扩展工具） |
