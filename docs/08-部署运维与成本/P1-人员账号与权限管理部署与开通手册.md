# P1 人员、账号与权限管理：服务器部署与首位系统管理员开通手册

适用：`crane-dev`（https://crane.youdaozd.com），源码直部署（不发镜像、不做 Candidate、不做 OCI 运输）。Schema 12 → 13（00013，前向迁移，部署前必须有 6 小时内的备份）。

本专项新增了一个**独立的系统权限域**：

| 系统角色 | 能做什么 | 不能做什么 |
|---|---|---|
| 系统管理员 `system_admin` | 人员与账号（开户、编辑、停用/启用、重置密码、撤销会话）、系统角色、项目组合角色、部门 | 不包含任何项目 / 项目组合业务数据访问；不能改自己的系统角色、不能停用自己；最后一名启用的系统管理员不能被停用或降级 |
| 账号管理员 `account_manager` | 为**普通人员**开户、编辑、停用/启用、重置密码、撤销会话 | 不能授予任何角色；不能操作持有系统角色的人员 |

项目角色（只读 / 操作员 / 维护员 / 项目管理员 `platform_admin`）与项目组合角色（规划者 / 经理）不变；`platform_admin` 仍只代表“项目管理员”，不带任何系统权限。项目成员仍由所在组合的项目组合经理授予，界面改为“搜索并选择人员”。

## 1. 部署（一次性，顺序 1.1 → 1.2 → 1.3 → 2）

### 1.1 新增私有 secret：账号服务凭据

cloud-api 通过 Keycloak `crane` realm 内的受限客户端 `crane-account-service`（client credentials）管理用户。它只持有 realm-management 的 `view-users / query-users / manage-users`，不能改 realm、客户端、角色、其他 realm，也不能给自己或他人提权（已在真实 Keycloak 26.8.1 上逐项验证，见 `docs/04-前端与可视化/evidence/p1-personnel/keycloak-26.8.1-real-run.txt`）。应用**从不**持有 master realm / bootstrap 管理员凭据。

```bash
sudo deploy/scripts/provision-secrets.sh /srv/u-dao/secrets/crane-ops
#   幂等：已有文件保持不变，只新建 account_service_secret（0600，属主 10001）。内容不会打印。
ls -l /srv/u-dao/secrets/crane-ops/account_service_secret
```

`docker-compose.prod.yml` 已为 cloud-api 增加：`ACCOUNT_SERVICE_CLIENT_ID=crane-account-service`、`ACCOUNT_SERVICE_SECRET_FILE=/run/secrets/account_service_secret`、`KEYCLOAK_INTERNAL_URL=http://keycloak:8080`（仅内部网络；公网 `/admin/` 仍被入口拒绝）。**secret 文件不存在时 compose 无法启动 cloud-api，务必先做 1.1。**

### 1.2 部署 SHA（含 00013 迁移）

**先备份并做隔离恢复演练**（真实 `deploy/scripts/backup.py`：应用库 + Keycloak 库双库、校验和、恢复到随机 `crane_drill_*` 临时库比对后删除，从不覆盖正式库）。备份的 `source_sha` 必须是**当前正在运行**的版本，local-dev-deploy 会核对：

```bash
cd /srv/u-dao/src/crane-operations-platform && git status --porcelain     # 必须为空
ENV=/srv/u-dao/secrets/crane-ops/crane.env; D=deploy/scripts/local-dev-deploy.mjs
RUN_SHA=$(python3 -c 'import json;print(json.load(open("/srv/u-dao/releases/crane-local/current.json"))["source_sha"])')
B=(python3 deploy/scripts/backup.py --project-name u-dao-crane-ops --compose deploy/compose/docker-compose.prod.yml --env-file "$ENV")
sudo "${B[@]}" backup --root /srv/u-dao/backups/crane-ops --source-sha "$RUN_SHA"
#   输出 BACKUP=PASS name=crane-backup-<时间>-<8位>
SET=/srv/u-dao/backups/crane-ops/$(ls -1 /srv/u-dao/backups/crane-ops | grep '^crane-backup-' | sort | tail -1)
sudo "${B[@]}" drill --backup "$SET"
#   输出 RESTORE=PASS isolated_databases=2 …  （失败则停止，不部署）
```

然后部署（备份须在 6 小时内；schema 12 → 13 时 apply 强制要求 `--backup`）：

```bash
git fetch origin && git checkout --detach <完整 40 位 SHA>
node $D build "$ENV" --goproxy https://goproxy.cn,direct
node $D plan  "$ENV"                   # 应显示 schema=12->13 migration=YES(backup required)
node $D apply "$ENV" --backup "$SET"
node $D status "$ENV"
```

部署后、执行 1.3 之前，cloud-api 已能启动（secret 文件已存在），但 Keycloak 中尚无 `crane-account-service`，开户/重置密码会返回 503「身份服务暂不可用」；执行 1.3 并重启 cloud-api 后恢复。已部署的其他功能不受影响。

### 1.3 在 Keycloak 中只初始化账号服务（不改现有登录与安全配置）

```bash
sudo deploy/scripts/provision-account-service.sh "$ENV"
#   逐项输出 UNCHANGED realm / client:crane-bff / required-actions / users+credentials sha256=…
#   最后一行：crane-account-service converged; realm, crane-bff, users and policies unchanged
node $D compose "$ENV" -- up -d --no-deps cloud-api      # 让 cloud-api 读取新凭据
node $D compose "$ENV" -- logs --tail 50 cloud-api | grep account_service_missing && echo "未生效" || echo "账号服务已启用"
```

说明与要求：

- 使用 `provision-keycloak --account-service-only`：**只**创建/收敛 `crane-account-service`（服务账号、realm-management 的 view-users / query-users / manage-users、scope mapping）并补充两个仅管理员可见的用户属性 `crane_managed`、`crane_user_id`（已存在则不动）。它不写 realm 设置（密码策略、暴力破解保护、会话时长、必需动作）、不写 `crane-bff` 客户端、不改任何用户和密码，也不读取 OIDC client secret。执行前后对上述对象分别取摘要比对，任何变化即失败退出（真实 Keycloak 26.8.1 上已验证：预置的自定义密码策略与会话时长、crane-bff、OWNER 账号与凭据均保持原样）。
- 一次性容器只挂载 bootstrap 管理员密码与账号服务 secret 两个只读文件，跑在 Crane 后端网络（`http://keycloak:8080`），不发布端口；cloud-api **从不**挂载 bootstrap 凭据。
- 若服务器早先已移除了 Keycloak 临时管理员，先在 keycloak 容器内用官方命令临时恢复（`/opt/keycloak/bin/kc.sh bootstrap-admin user …`，密码从 `keycloak_bootstrap_password` 文件读取），本节完成后再删除。
- 幂等：重复执行结果相同；若服务账号被人为加了其他角色，会被**收回**。
- 本模式不取消 email/姓名的“首次登录必填”。若 realm 的用户资料把 email 设为必填，员工首次登录在改密后会多一步填写邮箱，属正常。

## 2. 开通第一位系统管理员（解决“无法自行管理新增人员”）

把 OWNER 现有的、能登录的 Keycloak 账号纳管为系统管理员。不改密码、保留原有本地身份、授权与历史：

```bash
node $D compose "$ENV" -- run --rm --no-deps --entrypoint identity \
  -e DATABASE_URL=postgres://crane_app@postgres:5432/crane_app?sslmode=disable \
  -e DATABASE_PASSWORD_FILE=/run/secrets/app_db_password \
  -e OIDC_ISSUER=https://crane.youdaozd.com/realms/crane \
  -e ACCOUNT_SERVICE_SECRET_FILE=/run/secrets/account_service_secret \
  -e KEYCLOAK_INTERNAL_URL=http://keycloak:8080 \
  cloud-api adopt-admin --username <OWNER 的 Keycloak 用户名> --actor <操作人>
# 输出：System administrator ready: id=… username=… enabled=true; no credentials printed.
node $D compose "$ENV" -- run --rm --no-deps --entrypoint identity … cloud-api list-admins
```

- 如果 OWNER 目前**连 Keycloak 账号都没有/不能登录**：先在 Keycloak 管理台（用 1.3 的临时管理员）为其设置 Temporary 密码，再执行 `adopt-admin`。
- 之后所有人员都在网页「人员与账号」中开户；宿主机工具只用于恢复（例如误操作后没有可用的系统管理员）。
- 恢复工具同样受“最后一名系统管理员”保护：`system-role --id X --role system_admin --remove` 在 X 是唯一启用的系统管理员时会被拒绝。

## 3. 网页操作要点

- 入口：左侧栏「人员与账号」（仅系统角色持有人可见；接口一律在服务端校验）。
- 新增人员三步：基本信息（姓名、唯一登录用户名、部门、岗位、可选电话/邮箱）→ 权限配置（系统角色、项目组合角色）→ 账号开通。成功后**一次性显示**初始密码：系统不保存、不写日志、不进浏览器存储；关闭后无法再看，丢失就“重置密码”。员工首次登录必须改密。
- 开户中断（网络、Keycloak 不可用、浏览器关闭）：同一次提交重试即继续，不会产生第二个账号；列表顶部「未完成的开户」可继续或放弃（放弃会删除尚未授权、仍为停用状态的 Keycloak 账号并释放用户名）。任何中断点都不会出现“能登录但没有获批权限”的账号。
- 停用：立即删除该人员的所有平台会话、结束实时观看，Keycloak 账号停用并登出；已打开的页面下一次请求即 401，WebSocket 立即被关闭。历史业务记录和审计保留。重新启用**不会**恢复停用期间被撤销的授权。
- 重置密码：先结束所有平台会话与实时观看，再设置新的一次性密码并登出 Keycloak 会话；旧密码与旧会话立即失效。
- 身份服务暂时不可用时，停用仍在平台侧立即生效（显示“身份同步待重试”），在详情页重做同一操作即可完成同步。
- 所有操作写审计：操作人、目标人员、作用范围、变更摘要、requestId、来源 IP、结果；不记录任何密码或令牌。人员详情页「安全操作与历史」可查看。

## 4. 与零业务初始化（reset-business，R8 手册 §3A）的关系

reset-business 保留：人员（users 全部字段）、部门、系统角色、开户记录、项目组合角色、账号审计。重置后合法系统管理员可以继续登录、开户和管理人员（`TestResetDeletesBusinessDataKeepsFoundation` 已覆盖）。§3A.4 中“UAT 临时账号在 Keycloak 管理台单独停用”现在改为：在「人员与账号」中按名单停用（同时停用 Keycloak 账号并写审计）。

## 5. 服务器验收清单（部署后执行，结果贴回）

1. OWNER 账号 `adopt-admin` 后登录，侧栏出现「人员与账号」。
2. 网页开通一个全新账号（带一个项目组合规划者角色），记录一次性密码。
3. 新账号首次登录被要求改密，改密后进入平台；只看到被授予的项目组合。
4. 组合经理在正式项目中通过“搜索人员”授予该账号项目角色；页面与直接 API 均生效；对其他组合 / 项目返回 403/404。
5. 该账号保持登录（打开一个设备运行页），管理员停用它：页面下一次请求被踢出，实时流断开；Keycloak 登录被拒。重新启用后可登录，之前撤销的授权未恢复。
6. 重置密码：旧密码和旧会话失效，新一次性密码要求改密。
7. 用同一用户名再开户 → 提示“用户名已存在”。
8. 试图降级/停用最后一名系统管理员 → 被拒绝；匿名访问 `/api/v1/admin/people` → 401，普通账号 → 403。
9. 手机（375 宽）打开「人员与账号」及详情页，可正常操作。
10. （如执行 reset-business）重置后系统管理员仍能登录并开户。
