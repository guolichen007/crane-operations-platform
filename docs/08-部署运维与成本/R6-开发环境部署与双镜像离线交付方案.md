## 1. 镜像接收

**路径 A（首选）：服务器直接按 digest 拉取。** dev 命名空间包为公开匿名可拉（D1-RC1 已核）。`dev-upgrade apply` 内部执行 `compose pull cloud-api web-console`，引用为 env 中的 `image@sha256`，内容寻址，天然校验完整性。

**路径 B（仅当服务器无法访问 ghcr.io）：离线运输。** 关键约束：`docker save`/`docker load` 不保留 registry manifest digest（`RepoDigests` 为空），按 `@sha256` 引用的 compose 会再去拉取而失败。因此离线运输必须携带**原始 OCI 清单**并在服务器上恢复为可按 digest 解析的形式，不能只靠 `docker load`。做法：

1. 在可联网的受控机器（不是服务器）上，对每个镜像：
   ```bash
   set -euo pipefail; umask 077
   REF=ghcr.io/guolichen007/crane-operations-platform/dev/cloud-api@sha256:<CLOUD_DIGEST>
   skopeo inspect --raw "docker://$REF" | sha256sum      # 必须等于 <CLOUD_DIGEST>
   skopeo inspect --raw "docker://$REF" | jq '.manifests[]?.platform'   # 记录架构
   skopeo copy --all --preserve-digests "docker://$REF" "oci-archive:r6-cloud-api.oci.tar"
   sha256sum r6-cloud-api.oci.tar > r6-cloud-api.oci.tar.sha256
   ```
   web-console 同理。`--preserve-digests` 若因压缩重算被拒，停止，改走路径 A 或路径 C。
2. 运输两个 tar 及 `.sha256`、`dev-manifest.json`；服务器上先 `sha256sum -c`。
3. 在服务器上导入为本地仅回环可达的临时 registry（`registry:2` 已在本机镜像缓存中时才可用，监听 `127.0.0.1`，用完即删），`skopeo copy --preserve-digests oci-archive:… docker://127.0.0.1:5000/…`，再从该地址按同一 digest 拉取并 retag 为 manifest 中的完整引用；最后核对：
   ```bash
   docker image inspect <完整引用@sha256:DIGEST> --format '{{index .Config.Labels "org.opencontainers.image.revision"}} {{.Architecture}}'
   ```
   revision 必须等于 SOURCE_SHA，架构必须等于服务器 `uname -m` 对应值。
4. 这条路径改变了 `dev-upgrade apply` 的 pull 步骤，属于**未演练路径**：首次使用前必须在服务器上只做导入与核对（不 up），确认 `docker compose … pull --dry-run`/`config` 能解析到本地 digest 后再继续；任一步不符即停止回到路径 A。

**路径 C（备选）**：若受控机器无 skopeo，可用 `crane pull --format=oci`/`oras` 等保留 manifest 的工具，同样以 manifest 原文 sha256 = digest 为验收标准。

## 2. 升级（双库备份、双服务、env、运行记录）

在服务器仓库干净检出 SOURCE_SHA（`dev-upgrade` 会 `assertExactCheckout`）。全部命令 `set -euo pipefail; umask 077`。

1. `record`：`node deploy/scripts/dev-upgrade.mjs record /srv/u-dao/secrets/crane-ops/crane.env /srv/u-dao/releases/crane-prev-<旧SHA>.json`，固定当前两镜像 digest 与 schema（应为 12）。
2. 新鲜双库备份：`python3 deploy/scripts/backup.py …`（crane_app + keycloak，≤6 小时内、完成集 `crane-backup-*`），仅备份，不做任何恢复。
3. env 持久化：备份原 env（0600），仅把 `CRANE_CLOUD_IMAGE`、`CRANE_WEB_IMAGE` 改为 manifest 中两个 `@sha256` 引用；`CRANE_DEPLOYMENT_ENVIRONMENT=crane-dev` 不变。
4. `plan`：必须 `DEV_PLAN=PASS … migration=NO`。
5. `apply`：只拉取并 `--no-deps` 重建 cloud-api、web-console，自动 smoke（首页、OIDC discovery、API 401、/health 与 /admin 不公开）。
6. 运行记录：再执行一次 `record` 到 `crane-r6-<SOURCE_SHA>.json`，与备份路径、Candidate run id 一并归档。

## 3. 类型目录初始化（43 种）

严格按 `docs/08-部署运维与成本/R6-Equipment设备类型目录初始化操作手册.md`：`plan --all`（target 必须 crane_app/crane_app/12，toCreate=43，无冲突与未注册）→ `apply --all --approve <digest> --actor <管理员>`（result=success，created=43）→ `verify --all --expect-installable 43`（退出 0）→ 审计行核对。

## 4. UAT 身份与授权

新建两个独立匿名测试身份（Keycloak 用户，非临时密码由 OWNER 私下保管），用 `identity bind` 绑定 issuer+sub，`identity grant` 仅授权到**本轮指定的测试项目**（建议：UAT-A 为 platform_admin，UAT-B 为 viewer，用于权限与跨项目反证）。不授权历史九个示例项目，不改动现有三个 R5-UAT 项目与已有身份。

## 5. 业务测试范围（匿名测试数据）

所有测试数据使用统一前缀（如 `R6UAT-`），只在指定测试项目内：项目登记与授权可见、资产新建/编辑、位置中心建 场地→车间、资产移动后「当前位置」与「位置历史」、位置父节点改挂（合法 200，成环 422）、安装 Equipment（43 类型可选、停用类型不可装需单独批准停用操作，否则跳过）、编辑/拆卸、退役后位置仍可读、viewer 只读与跨项目 404、告警页只读核对。不删除测试项目（只退役/停用）。浏览器脚本可复用 `tests/e2e/b4/r6-business-closure.spec.ts` 的步骤与精确定位方式。

## 6. 回退（无迁移镜像回退）

条件：数据库 schema 仍为 12（本轮无迁移）。在保留的旧 SHA 控制检出中恢复旧 env，执行 `dev-upgrade.mjs rollback <env> crane-prev-<旧SHA>.json`；工具会核对 env 镜像等于固定的旧 digest、schema 未变化，再只重建两服务并 smoke。已初始化的 43 个类型与 R6 新增的移动修订/时间线行保留，旧镜像不读取它们，不影响运行。**不做数据库覆盖恢复**。
