- 00015：首台资产导入、点位、计量、维护规则、预警、工单、更换、钢丝绳。

> **禁止事项（本手册全程有效）**

> - 不执行全量 `reset-business`，不覆盖恢复正式库，不动其他平台和共享入口。

## 0. 约定（所有命令在部署检出目录执行）

```bash
set -euo pipefail; umask 077
cd /srv/u-dao/src/crane-operations-platform && git status --porcelain     # 必须为空
ENV=/srv/u-dao/secrets/crane-ops/crane.env; D=deploy/scripts/local-dev-deploy.mjs
WORK=/srv/u-dao/releases/r9-lhk-$(date +%Y%m%dT%H%M%S)
install -d -m 0711 "$WORK"         # 容器用户 10001 只能按文件名进入，不能列目录
DBENV=(-e DATABASE_URL='postgres://crane_app@postgres:5432/crane_app?sslmode=disable' -e DATABASE_PASSWORD_FILE=/run/secrets/app_db_password)
# 一次性主机工具一律经 local-dev-deploy compose（带 ACTIVE override，自动加 --pull never）：
TOOL() { node $D compose "$ENV" -- run --rm --no-deps --entrypoint "$1" "${DBENV[@]}" "${@:2}"; }
```

**挂载与可读性**

- 挂载一律写 `--volume 宿主机绝对路径:容器路径:ro`。maintenance compose 会**拒绝 `-v`**，因为 `-v` 在 `down` / `rm` 里的含义是删卷。它同样拒绝具名卷、`/var/run` 和 `/proc` 等路径，以及不是 `run` 的 `--volume`。
- 工具容器以 UID **10001** 运行。挂载进去的文件必须对 10001 可读：要么文件归 10001 所有，要么权限是 0644（这里的文件都不含机密）。目录用 0711。可以先自检：

```bash
check_readable() { local u m; read -r u m < <(stat -c '%u %a' "$1"); [[ "$u" == 10001 ]] || (( 8#$m & 8#004 )) || { echo "不可读：$1（chmod 0644 或 chown 10001）"; return 1; }; }
```

- 数据库密码只从容器内已挂载的 `/run/secrets/app_db_password` 读取。它不出现在命令行、环境变量值和 shell 历史中。

## 2. Broker 镜像预加载与部署

```bash
# 2.1 预加载固定 digest（只拉 images.json 里的 eclipse-mosquitto:2.0.23@sha256:6a332cc7…ad9，不动任何容器）
node deploy/scripts/broker-ops.mjs preload "$ENV"          # BROKER_IMAGE_PRELOAD=PASS image=…
# 2.2 构建与部署（Schema 13 → 16）
git fetch origin && git checkout --detach <完整 40 位 SHA>
node $D build "$ENV" --goproxy https://goproxy.cn,direct
node $D plan  "$ENV"                      # 应显示 schema=13->16 migration=YES(backup required)
node $D apply "$ENV" --backup "$SET"
node $D status "$ENV"
```

- apply 前会执行依赖门禁（`DEPENDENCY_GATE PASS|FAIL`），检查 postgres、keycloak、mosquitto 三个服务都在运行且健康。FAIL 时退出码为 3，不切换镜像。
- **apply 不重建 mosquitto。** 要升级 Broker，先运行 `broker-ops.mjs status` 看是否有定义漂移（镜像不等于固定 digest、没有健康检查、或重启策略不是 unless-stopped）。有漂移时在维护窗口执行：

```bash
node deploy/scripts/broker-ops.mjs recover "$ENV" --reason "R9 升级 mosquitto 2.0.23" --actor <管理员>
#   BROKER_RECOVERY=PASS action=recreate image=…2.0.23@sha256:… health=healthy cloud_mqtt_connected=1
```

  recover 重建时**固定使用 `--pull never`**，从不拉取镜像。本地没有固定 digest 的镜像时，它直接拒绝并提示先执行 `preload`。持久化卷、mTLS 材料和 ACL 都不变。恢复前的状态和最近 200 行日志保存为 0600 文件。Broker 健康且无漂移时，recover 也会拒绝执行（除非显式加 `--force`）。

- 断言问题没有日志，在 2.0.22 和 2.0.23 上各做了 5000 多次重连压测，**未复现**。

**项目归属（`projectScope`）**

LHK 只登记为 **Inventory 项目**，`projectScope` 的期望值是：`portfolioScopeId=null`、`intakeRecords=0`、`approvalAudits=0`、`projectMembers=0`。

导入**不创建**项目组合关系、立项记录、审批记录或验收历史。verify 发现其中任何一项不为 0，都会判为不一致（退出码 3）。

如果业务上需要把 LHK 纳入某个项目组合，必须走网页的立项和审批流程，由组合经理办理，不能直接改库。

**初始归属与后续合法授权的区别**

导入完成时，LHK 的状态是“已登记但无人授权”。导入只做第一步，后面三项都是独立的、有审计的授权动作：

| 层次 | 导入后的初始状态 | 谁、通过什么方式改变 | 留痕 |
|---|---|---|---|
| 项目归属 | Inventory 项目（`lifecycle=PLANNED`、行政区 420682）；`portfolio_scope_id=NULL`；没有立项单 | 只能走网页「项目组合 → 立项登记 → 审批」，由组合经理办理；导入工具与本手册的任何命令都不写这一层 | 立项流转记录与审批审计 |
| 项目成员权限 | 0 人（`projectMembers=0`），只有系统管理员能看到人员页，看不到资产 | 网页项目权限页由有权限的经理授予，或在宿主机执行 `identity grant --project LHK --role …`（审计 actor 为 `host:<管理员>`） | `project_memberships` 与授权审计 |
| 资产主数据确认（铭牌 / 点位 / 规则审批） | 全部待确认；53 条草案未批准 | 平台管理员在「接入准备」逐项确认（§7） | 修订记录、审计、`point_config_changes` |

注意：

- verify 输出的 `projectScope` 只用来证明导入**没有**伪造上层归属或审批，不代表项目已经立项或已授权。
- 授予权限不改变项目归属；纳入项目组合也不会自动给任何人授权。
- 不得直接修改数据库的 `portfolio_scope_id` 或补写立项、审批、验收记录。

建议授权：现场维护人员授予 maintainer，只读人员授予 viewer，负责确认铭牌和审批规则的人授予 platform_admin。

## 6. G2 模拟维护闭环：受控场景初始化 → 真实 MQTT → 验收 → 清理 / 重跑

`lhk-sim` 只做三件事：

- 写入带 `SIM-SCN-*` 标记的 **test_only** 规则（数据库 CHECK 保证这类规则不能被批准，也不能用于 REAL）；
- 为这些规则写入 SIMULATION 初始基准；
- 写审计。

它**不写遥测，也不做评估**。计量只从模拟器经 Mosquitto（mTLS + ACL）进入云端，预警由云端维护循环产生。

```bash
TOOL lhk-sim cloud-api plan > "$WORK/sim-plan.json"
jq '.plan | {runtime, runtimeMode, problems, rules, baselines, realDraftRules, digest}' "$WORK/sim-plan.json"   # problems 必须为 []；realDraftRules=53（只读显示）
TOOL lhk-sim cloud-api apply --approve "$(jq -r .plan.digest "$WORK/sim-plan.json")" --actor <管理员> > "$WORK/sim-apply.json"
# 启动模拟器（验收加速：1 秒一批，每真实秒 = 2 模拟分钟；日常演示用 --meter-speedup 1）
node $D build "$ENV" --services device-simulator --goproxy https://goproxy.cn,direct
deploy/scripts/sim-control.sh start "$ENV" --fleet $S/sim-run-fleet.json --certs $S/certs --scenario normal --meter-seconds 5 --meter-speedup 60
# 约 2–5 分钟后验收（PENDING 表示计量未到阈值，等待后重跑；只读）
TOOL lhk-sim cloud-api verify --fresh-minutes 10 | tee "$WORK/sim-verify.json"; echo "exit=${PIPESTATUS[0]}"   # 0 PASS · 3 PENDING · 4 FAIL
```

| 场景规则 | 类型 | 预期 |
|---|---|---|
| SIM-SCN-TIME | 时间（365 天，模拟安装 360 天前） | `LEAD_7` 提醒 |
| SIM-SCN-CYCLES | 次数（GANTRY-01 总接触器，阈值 1000，模拟初始 960） | 经 MQTT 计数后 `PCT_100` |
| SIM-SCN-HOURS | 小时（GANTRY-03 变频器，阈值 100 h，模拟初始 99.8 h） | 经 MQTT 累计后 `PCT_100` |
| SIM-SCN-HYBRID | 混合（30 天 / 10 万次，时间先到） | `LEAD_7` |
| SIM-SCN-HYBRID-PARTIAL | 混合，计量初始使用量**未知** | 已知的时间条件到期，产生 `OVERDUE`；状态显示「部分数据不足」，计量部分不当作 0 |
| SIM-SCN-CAL | 校准（称重传感器，180 天） | `LEAD_7`；维护中心类别为 `CALIBRATION_DUE` |

verify 还会核对以下几项：

- 57 个计量项都通过 MQTT 收到数据，且最新一批不超过 `--fresh-minutes`；
- LHK-CRANE-001 上没有任何 REAL 运行身份、计量、预警或工单；
- 场景规则全部是 test_only，没有任何真实规则被主机工具批准；
- 读数没有重复。

输出最后一行为 `LHK_SIM_SCENARIO=PASS REAL_HARDWARE=NONE`。

**网站验收**（maintainer 账号）：

1. 打开资产详情 → 运行监测：所有数据都标「模拟数据」。
2. 寿命与维护：能看到上表的预警；对 `PCT_100` 生成工单 → 分配 → 开始 → 完成，并勾选更换。完成后规则进入第 2 周期。
3. 历史：能看到工单流转和「更换（模拟数据）」两类记录。
4. 维护与到期中心：默认只显示真实数据；切换到「全部」后出现模拟行。

**清理与重跑**（只清理本场景，范围精确）：

```bash
deploy/scripts/sim-control.sh stop "$ENV"
TOOL lhk-sim cloud-api cleanup-plan --include-meter-data > "$WORK/sim-cleanup-plan.json"
jq '.plan | {counts, digest}' "$WORK/sim-cleanup-plan.json"
TOOL lhk-sim cloud-api cleanup-apply --include-meter-data --approve "$(jq -r .plan.digest "$WORK/sim-cleanup-plan.json")" --actor <管理员>
# 重跑：回到本节开头 plan → apply → start → verify
```

清理范围如下：

- `SIM-SCN-*` 规则，以及它们的 SIMULATION 排程、预警、工单、流转、模拟更换和钢丝绳检查；
- LHK-CRANE-001 的 SIMULATION / TEST 基准；
- 加 `--include-meter-data` 时，再加上 SIM-LHK-CRANE-001 自己的模拟读数、日值、计数事件和故障。

**REAL 数据、导入台账、55 行原文和 53 条草案永远不在清理范围内。** 清理会写审计 `lhk_sim_scenario_cleaned`。模拟器本地累计的计数器保存在 spool 卷里；如果要从样例首值重新开始，需在停止模拟器后删除 `u-dao-crane-ops_crane-simulation-spool` 卷（R8 手册 §2.5）。

## 7. G3 实车接入准备（网页「资产详情 → 接入准备」，平台管理员）

每项操作都要求平台管理员权限、依据文字和 If-Match 版本，并写入实体修订历史和审计。版本冲突时返回 409，页面会自动刷新后提示重新核对。

| 事项 | 入口 | 规则 |
|---|---|---|
| 铭牌参数（10 t / 31 m 候选）与实际位置 | 铭牌与待确认属性 → 确认 / 否决 | 确认的额定起重量和跨度写入资产台账，并留修订记录 |
| 器件实际安装日期 | 器件实际安装日期 → 登记 | 不得晚于今天；不使用导入时间 |
| 点位地址、有效电平、边沿、数据类型、单位 | 点位现场确认 → 确认 / 否决 | 位地址必须填有效电平，计次点位还必须填计数边沿；该点位所有未处理的核查事项要随同一次配置变更处理，处理记录与变更编号关联；确认后计量项启用，否决后计量项停用 |
| 初始计量基准 | 初始计量基准 → 登记 | REAL 基准必须填写现场读数和依据；初始使用量未知就不登记，相应规则显示「数据不足」，不会当作 0 |
| 维护规则审批 | 维护规则审批 → 审批 | 逐条填写周期、生效日期和依据，按规则版本做乐观锁；53 条草案在逐条审批之前一直不生效 |
| 法定检验 | 法定检验 → 登记 / 更新 | 填写使用登记号、最近检验日期和有效期；同时关闭对应的待确认属性 |
| 计数复位确认 | 计数异常待确认 → 确认计数复位 | 只在 PLC 计数确实清零时操作；进程重启不算复位 |

**未经现场确认的点位**可以用于模拟验收，但**不能作为可信的 REAL 维护计量**。对这类点位，即便有 REAL 数据，规则也只显示「数据不足」，不会产生 REAL 预警。

阻断项清单在 §7 的「接入准备状态」中实时显示。全部清零前，系统不会把 REAL 计量当作维护依据。

## 8. 测试账号清理（显式名单 + 显式标记）

```bash
cat > "$WORK/cleanup.json" <<'JSON'
{ "reason": "R9 清理 UAT 测试账号（OWNER 批准名单）",
  "accounts": [ { "id": "<用户ID>", "username": "<用户名>" } ] }
JSON
chmod 0644 "$WORK/cleanup.json"; check_readable "$WORK/cleanup.json"
IDT() { node $D compose "$ENV" -- run --rm --no-deps --entrypoint identity "${DBENV[@]}" -e OIDC_ISSUER=https://crane.youdaozd.com/realms/crane \
  -e ACCOUNT_SERVICE_SECRET_FILE=/run/secrets/account_service_secret -e KEYCLOAK_INTERNAL_URL=http://keycloak:8080 "$@"; }
IDT cloud-api protect --id <OWNER 用户ID> --reason OWNER --actor <管理员>                 # 一次性：保护 OWNER 与服务身份
IDT cloud-api mark-test --id <用户ID> --username <用户名> --actor <管理员>               # 名单内每个测试账号逐个显式标记
IDT --volume "$WORK/cleanup.json:/work/cleanup.json:ro" cloud-api cleanup-plan --list /work/cleanup.json > "$WORK/cleanup-plan.json"
jq '.items[] | {username, action, reason, references}' "$WORK/cleanup-plan.json"
IDT --volume "$WORK/cleanup.json:/work/cleanup.json:ro" cloud-api cleanup-apply --list /work/cleanup.json \
  --approve "$(jq -r .digest "$WORK/cleanup-plan.json")" --actor <管理员>
```

- `mark-test` 对以下身份一律拒绝：受保护身份（OWNER / SERVICE / SYSTEM）、系统管理员、ID 与用户名不一致的条目。
- 名单中没有标记为测试账号的人（正式员工）会被 plan 判为 `REFUSED`，因此整份 apply 都不会执行。
