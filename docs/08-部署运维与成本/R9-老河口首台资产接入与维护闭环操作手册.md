# R9 老河口首台资产接入与维护闭环操作手册（crane-dev）

适用范围：`crane-dev`（https://crane.youdaozd.com），分支 `feature/crane-r9-lhk-first-asset` 及之后的已提交 SHA。部署方式与 R8 相同，即源码直接部署（`deploy/scripts/local-dev-deploy.mjs`）：不发布镜像、不推 GHCR、不打 Tag。

数据库从 Schema 13 升到 15，分两个迁移，只做加法：
- 00014：人员归档 / 永久删除。
- 00015：首台资产导入、点位、计量、维护规则、预警、工单、更换、钢丝绳。

迁移不改写 00013，也不删除或改写任何已有数据。

> **禁止事项（本手册全程有效）**
>
> - 不执行全量 `reset-business`。导入只新增 LHK 项目，不清除其他项目。
> - 不覆盖恢复正式库。
> - 不动其他平台和共享入口。
> - 不开启真实机械控制。
> - 不把模拟数据写进 REAL 计量、维护或合规。
> - 不接入真实硬件（`REAL_HARDWARE_CONNECTED=NO`）。
> - 清理测试账号只认显式名单，不使用模糊匹配。
> - 临时密码不进日志或截图。

本手册的每一步都有可核对的输出。按回执记录时，未执行的项一律写 `NOT_RUN`，不写 PASS。

## 1. 备份与隔离恢复演练（迁移 13 → 15 前必做）

```bash
RUN_SHA=$(python3 -c 'import json;print(json.load(open("/srv/u-dao/releases/crane-local/current.json"))["source_sha"])')
B=(python3 deploy/scripts/backup.py --project-name u-dao-crane-ops --compose deploy/compose/docker-compose.prod.yml --env-file "$ENV")
sudo "${B[@]}" backup --root /srv/u-dao/backups/crane-ops --source-sha "$RUN_SHA"      # BACKUP=PASS name=crane-backup-…
SET=/srv/u-dao/backups/crane-ops/$(ls -1 /srv/u-dao/backups/crane-ops | grep '^crane-backup-' | sort | tail -1)
sudo "${B[@]}" drill --backup "$SET"                                                     # RESTORE=PASS isolated_databases=2 …
```

演练会把应用库和 Keycloak 库都恢复到随机命名的 `crane_drill_*` 临时库，比对后删除，从不覆盖正式库。若演练失败，**停止**，不部署。

## 2. 部署（含 Broker 依赖门禁）

```bash
git fetch origin && git checkout --detach <完整 40 位 SHA>
node $D build "$ENV" --goproxy https://goproxy.cn,direct
node $D plan  "$ENV"                      # 应显示 schema=13->15 migration=YES(backup required)
node $D apply "$ENV" --backup "$SET"
node $D status "$ENV"
```

- apply 切换镜像前会自动执行依赖门禁（`broker-ops.mjs` 的 `dependencyGate`），检查 postgres、keycloak、mosquitto 三个容器都在运行且健康（没有配置健康检查的容器以 running 为准）。日志输出 `DEPENDENCY_GATE PASS|FAIL …`。FAIL 时 apply 以退出码 3 停止，不切换镜像。先运行 `broker-ops.mjs preflight` 看完整检查项，包括镜像是否等于固定 digest、重启策略、ACL 与证书是否可读、cloud-api 是否已连接。
- 本 SHA 的 compose 把 mosquitto 镜像固定为 `eclipse-mosquitto:2.0.23@sha256:6a332cc7…ad9`，并新增健康检查（`nc -z 127.0.0.1 8883`）。mTLS、ACL 和持久化配置都没有改动。
- **apply 不会重建 mosquitto**，Broker 升级必须单独操作。先核对镜像差异：

```bash
node deploy/scripts/broker-ops.mjs status "$ENV"   # running/health/image/restart policy、cloud mqtt_connected
```

  若运行中的镜像不等于固定 digest（仍是 2.0.22），或者没有健康检查、重启策略不是 unless-stopped，就属于定义漂移。此时选一个维护窗口执行以下命令。它只重建 mosquitto，持久化卷、mTLS 材料和 ACL 不变，现有连接会短暂断开后自动重连：

```bash
node deploy/scripts/broker-ops.mjs recover "$ENV" --reason "R9 升级 mosquitto 2.0.23" --actor <管理员>
#   输出 BROKER_RECOVERY=PASS action=recreate image=… health=healthy restart_policy=unless-stopped cloud_mqtt_connected=1 evidence=…/recover-<时间>.json
#   失败时退出码 3；恢复前的状态和最近 200 行日志保存在私有状态目录（0600）
#   Broker 健康且没有漂移时，recover 会拒绝执行（需显式 --force）
```

- Broker 日常监测：cloud-api 的 `/metrics` 新增 `mqtt_connected`、`mqtt_connect_failures_total`、`mqtt_down_seconds` 三项。这些指标只能在内网读取，`/metrics` 不对外开放。`broker-ops.mjs preflight` 是只读检查。原先的断言问题没有日志可查，在 2.0.22 和 2.0.23 上做过 5000 多次重连压力测试也**未能复现**。

## 4. 老河口项目与首台资产导入（plan → apply → verify）

```bash
install -m 0644 /path/to/老河口行车监控平台点位.xlsx "$WORK/lhk.xlsx"     # 只用于核对 SHA256
OB=(node $D compose "$ENV" -- run --rm --no-deps --entrypoint onboarding \
    -e DATABASE_URL='postgres://crane_app@postgres:5432/crane_app?sslmode=disable' \
    -e DATABASE_PASSWORD_FILE=/run/secrets/app_db_password -v "$WORK":/work:ro cloud-api)
"${OB[@]}" plan --xlsx /work/lhk.xlsx > "$WORK/lhk-plan.json"
jq -e '.xlsxChecked and .plan.target.database=="crane_app" and .plan.target.schemaVersion==15 and (.plan.conflicts|length)==0' "$WORK/lhk-plan.json"
jq '.plan | {new, sourceSha256, stagingSha256, digest}' "$WORK/lhk-plan.json"
```

首次导入时，`new` 应等于下表（与同 SHA 在隔离库上的实测一致）：

| 对象 | 数量 | 说明 |
|---|---|---|
| project / site / asset | 1 / 1 / 1 | 项目 `LHK`（老河口行车项目，湖北省襄阳市老河口市 420682），站点 `LHK-SITE`，资产 `LHK-CRANE-001` |
| source_row | 55 | 原始 55 行全部按原文保存，包括 PLC 地址原文和寿命原文 |
| equipment | 51 | 51 行设备来源；另外 4 行作业记录（P052–P055）不生成设备 |
| point | 55 | 点位；DBX 位、整字、无地址、无法解析的地址分别标注 |
| meter | 57 | 计量定义，均处于待核状态；吨数口径冲突单独标为 `UNIT_CONFLICT_PENDING` |
| rule | 53 | 寿命 / 维护规则草案，状态 `DRAFT_UNAPPROVED`，**不生效**、不评估 |
| pending | 11 | 待确认属性：10t / 31m 只作为候选，NULL 值待铭牌确认；还包括位置、法定检验等 |
| manufacturer / catalog | 11 / 22 | 品牌与型号目录 |
| issue（counts） | 82 | 核查项，包括重复地址组、缺位索引、单位冲突等 |

如果 plan 出现 `conflicts`，或者 xlsx 的 SHA256 不一致，**停止**，不得缩小范围绕过。

```bash
"${OB[@]}" apply --approve "$(jq -r .plan.digest "$WORK/lhk-plan.json")" --actor <管理员> > "$WORK/lhk-apply.json"
jq -e '.record.result=="success" and .record.assetId=="LHK-CRANE-001"' "$WORK/lhk-apply.json"
"${OB[@]}" verify > "$WORK/lhk-verify.json" && echo "LHK_VERIFY=PASS" || echo "LHK_VERIFY=FAIL exit=$?"   # 3=漂移（停止核查）
jq '.report.consistent' "$WORK/lhk-verify.json"
"${OB[@]}" plan > "$WORK/lhk-replan.json"                              # 幂等：new 为空 {}，conflicts 为空
```

导入可以重复执行：同一份清单第二次 apply 的结果是 `noop`，不会产生重复对象。

导入后，需在网站上为相关人员授予项目 `LHK` 的权限（项目权限页，或用 `identity grant`）。只读人员用 viewer，维护人员用 maintainer。

## 5. 首台模拟运行身份 SIM-LHK-CRANE-001

按 R8 手册 §2.1–§2.5 执行，请求文件改为：

```json
{ "tenantId": "demo", "entries": [ { "runtimeDeviceId": "SIM-LHK-CRANE-001", "projectId": "LHK",
  "assetDeviceId": "LHK-CRANE-001", "sourceMode": "SIMULATION" } ] }
```

需要依次完成以下步骤：

1. `runtime-identity` 执行 plan、apply、verify。
2. 合并云端 Fleet 与模拟器运行 Fleet（运行 Fleet 只含 SIM-LHK-CRANE-001）。
3. `node $D fleet` 更新 Fleet 与 ACL。
4. 用 `sim-cert.sh issue` / `verify` 签发并核验证书（`--id SIM-LHK-CRANE-001`）。
5. 用 `sim-control.sh start … --scenario normal` 启动模拟器。

绑定到 `LHK-CRANE-001` 的 SIMULATION 运行身份会每 60 秒发送一批 `meter` 消息（`SIM_METER_SECONDS`，默认 60）。数据来自经过评审的样例 `lhk-normalized-simulation-v1`，由边缘端累计；离线时先进 spool 缓存，补传时按 bootId 加 sequence 幂等去重，计数不会归零。

网站验收标准：

- 资产详情 → 运行监测：每一项都标「模拟数据」，横幅醒目，并显示「无真实数据」。
- 真实计量保持为空。
- 维护与到期中心默认只显示真实数据，模拟数据不计入真实统计。
- 首页关注区的维护和检验项来自真实数据；没有数据时显示「未登记」或「数据不足」，不显示假数字。

## 6. 测试账号清理（显式名单）

```bash
cat > "$WORK/cleanup.json" <<'JSON'
{ "reason": "R9 清理 UAT 测试账号（OWNER 批准名单）",
  "accounts": [ { "id": "<用户ID>", "username": "<用户名>" } ] }
JSON
chmod 0644 "$WORK/cleanup.json"
ID=(node $D compose "$ENV" -- run --rm --no-deps --entrypoint identity \
  -e DATABASE_URL=postgres://crane_app@postgres:5432/crane_app?sslmode=disable \
  -e DATABASE_PASSWORD_FILE=/run/secrets/app_db_password \
  -e OIDC_ISSUER=https://crane.youdaozd.com/realms/crane \
  -e ACCOUNT_SERVICE_SECRET_FILE=/run/secrets/account_service_secret \
  -e KEYCLOAK_INTERNAL_URL=http://keycloak:8080 -v "$WORK":/work:ro cloud-api)
"${ID[@]}" protect --id <OWNER 用户ID> --reason OWNER --actor <管理员>     # 先保护 OWNER 和服务身份（只需一次）
"${ID[@]}" cleanup-plan --list /work/cleanup.json > "$WORK/cleanup-plan.json"
jq '.items[] | {username, action, reason, references}' "$WORK/cleanup-plan.json"
"${ID[@]}" cleanup-apply --list /work/cleanup.json --approve "$(jq -r .digest "$WORK/cleanup-plan.json")" --actor <管理员>
```

plan 对每个账号给出以下五种 action 之一：

- `ARCHIVE_AND_PURGE`：没有业务引用，可以永久删除。
- `ARCHIVE_ONLY`：有业务历史引用，只做归档并保留历史。
- `PURGE`：已归档，且没有引用。
- `KEEP_ARCHIVED`
- `REFUSED`：本人、最后一个管理员或受保护身份。

用户名与 ID 不一致的条目也会被拒绝。apply 只执行刚审阅过的那份 digest。归档时会撤销该账号的授权、会话和实时查看，并禁用登录。账号的历史记录保留，默认列表中不再显示。

在网页上「删除」人员时实际执行的是归档，只有 system_admin 可以操作。人员详情页的永久删除只对没有任何引用的测试账号开放。
