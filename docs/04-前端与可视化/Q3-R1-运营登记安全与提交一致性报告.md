## A. 运营登记授权检查与写入之间的竞态（TOCTOU）

**修复前**（在 `df63dd8` 上运行新增的确定性测试）：

```
registration after grant revoked:   200 {"id":"FP-A",...,"adminCode":330481,...}
registration after role downgraded: 200 {...}
registration after user disabled:   200 {...}
--- FAIL: TestInventoryRegistrationRevokedBeforeLockIsRefusedHTTP
```

用法：请求通过 HTTP 层的 location_write 检查后，在项目行锁上等待；此时另一个事务撤销授权、把角色降为 viewer，或停用用户。旧代码仍然登记成功。

**修复**：`inventory.RegisterFormalProject` 现在接收 `RegisterAuth{User, Allowed}`，在**同一个写事务**里完成以下步骤：

1. `SELECT … FROM projects … FOR UPDATE OF p`：锁定项目行。原有保护全部保留：必须是已批准登记对应的正式项目、项目组合和租户一致、`lifecycle IS NULL`。
2. `SELECT m.role FROM project_memberships m JOIN users u … AND u.enabled FOR SHARE OF m, u`：按数据库中**最新的**成员关系和用户状态读出角色，再用 `HasCapability(role, location_write)` 判断。没有成员关系、已停用或已降级时返回 `ErrRegistrationDenied`，接口返回 403 并写 `authorization_denied` 审计。
3. 更新 Inventory 字段，写审计，在事务内生成响应，提交。

HTTP 层的检查只是快速路径，最终以事务内的检查为准。不信任请求体和前端缓存。

**锁顺序**：登记和授权变更都按「项目行 → 用户行和成员行」的顺序加锁，所以两者不会互相等待形成死锁。

- 登记：`projects FOR UPDATE` → `users / project_memberships FOR SHARE`。
- Q2 的 `ChangeGrantGuarded`：`LockManageableProject` 锁 `projects FOR UPDATE`，之后锁 `users FOR UPDATE`，再写成员行。
- 宿主机的 `ChangeGrant`（不锁项目）：`users FOR UPDATE` → 写成员行。它和登记只在 users 或成员行上竞争：登记持有 FOR SHARE 时，撤销必须等待；撤销先提交时，登记读到的是撤销后的状态。

**修复后的证据**（真实 PG + BFF，连续跑 5 次稳定）：

| 测试 | 证明 |
| --- | --- |
| `TestInventoryRegistrationRevokedBeforeLockIsRefusedHTTP`：撤销、降级、停用 3 个子场景 | 请求已通过 HTTP 检查并在锁上等待；授权变更提交后释放锁，请求继续执行，结果为 **403**；项目字段不变，没有成功审计 |
| `TestInventoryRegistrationRevokeAfterLockSerializesHTTP` | 登记已持有锁时，宿主机撤销**必须等待**（测试先确认撤销没有提前返回）；放行后登记返回 200，撤销随后成功；审计 id 显示「登记先于撤销」 |

## B. 提交成功后再读取失败

**修复前**（在 `df63dd8` 上，于原有的提交后 `Projects()` 读取处注入失败）：

```
BEFORE-B: HTTP 503 {"error":"database unavailable"}
BEFORE-B retry: HTTP 409 {"error":"project is already registered in Inventory"}
```

登记其实已经提交，但用户看到的是「数据库不可用」；重试时又收到「已登记」。

**修复**：响应在**提交前、同一事务内**生成，事务能看到自己刚写入的数据，计数与 `Projects()` 共用同一条查询。提交之后不再做任何读取。

- 生成响应失败时整体回滚，结果确定是「未登记」，可以安全重试。
- 提交成功就一定返回 200。

计数全部来自数据库，不做推测：资产、运行身份、REAL 在线、模拟。

**前端**：

- 503 现在明确提示「登记未完成（未做任何修改）」。
- 网络失败或 409（结果未知或已登记）时，表单**先向服务端确认**：重新拉取待登记列表。如果该项目已不在待登记中，就关闭表单并提示「已登记（服务端确认）」，不再提交；如果无法确认，就提示「请勿重复提交」。
- 确认期间提交按钮禁用。

**修复后的证据**：

- `TestInventoryRegistrationResponseReadFailsRollsBackHTTP`：注入事务内读取失败后返回 503，项目字段不变，没有成功审计；重试返回 200（计数 0/0）；再次提交返回 409；审计恰好 1 条。
- `TestInventoryRegistrationFlowAndConsistencyHTTP` 仍然通过：登记响应中 assetDeviceCount=2，和 `/projects`、summary 一致。
- 浏览器 `premium/inventory-registration.spec.ts` 新增「登记已提交但响应丢失」：模拟服务端已提交、连接被重置。页面确认状态后关闭表单，POST 只发了 1 次，项目卡片出现。截图 `evidence/q3-inventory/7-commit-confirmed.png`。
