统计对象是**项目预估金额中已确认的部分**（人民币元），不是合同金额、销售收入、回款、利润、赢单率或成交预测。WON 只是销售阶段，不代表合同收入。

## 1. 金额字段来源与历史兼容规则（B0 法证）

| 来源 | 定义 | 写入 / 读取 |
| --- | --- | --- |
| `intake_projects.estimated_amount` | `numeric(18,2)`，元（00001） | 创建 INSERT、编辑 PATCH、提交 UPDATE 均写入 `in.EstimatedAmount`（Go `*float64`），PostgreSQL 隐式舍入到 2 位；`stage-change` 不写该列 |
| `document.estimatedAmount` | JSON 数值 | 与上同一事务写入 `mustJSON(in)`，即 float64 的最短十进制表示 |
| `document.knowledge.estimatedAmount` | `KNOWN` / `UNKNOWN` / `LEGACY_UNCONFIRMED` | `validateInput → inputKnowledge → knowledgeState`（`project_model.go`）在写入前规范化；读取时 `scan()` 再次执行同一规则，矛盾即报错 |

G1 已批准规则（16 号 ADR-005、19 号文档、`TestNumericKnowledgeCompatibility`）：无标记时 `null → UNKNOWN`、`0 → LEGACY_UNCONFIRMED`、正数 → `KNOWN`；显式标记必须与值一致（`UNKNOWN` 只配 null，`KNOWN` 配任意非空值，`LEGACY_UNCONFIRMED` 只配 0）。00004 迁移没有回填 knowledge；历史 0 仍是 0 并按上述规则读作待确认，正数按 KNOWN 读。前端 `NumberField` 单位“元”，空 = UNKNOWN，任何输入 = KNOWN，历史 0 需点“确认为 0”才变为 KNOWN；`validateInput` 允许 0–1e14。

**写入精度实测（PG18）。** `float64 → numeric(18,2)`：0、0.01、0.10、125000.25、1e14 列与文档一致；`0.125 → 列 0.13 / 文档 0.125`，`12345678.9999 → 列 12345679.00 / 文档 12345678.9999`；`90071992547409.91 → 两处均 …409.90`（float64 在约 9e13 以上丢分，列与文档一致，属输入端精度损失）。

**判定规则。** 一个项目的金额只有在“已知性符合 G1 规则”且“列与文档数值精确相等（numeric 比较）”且在 0–1e14 内时才计为对应类别；其余一律 INVALID（数据异常，不计入合计，不改写）。实现两份：SQL `amountClassSQL()`（统计用，先 `jsonb_typeof` 再转换，结构损坏的文档不会让查询失败）与 Go 参考 `amountClass()`（真实 `Input` 模型 + `numericKnowledge` + `big.Rat` 精确比较）。

## 2. 判定表

| 类别 | 条件 | 计入 knownTotal | 计数 |
| --- | --- | --- | --- |
| KNOWN | 显式 KNOWN 且值非空，或无标记正数（G1 规则）；列 = 文档 | 是 | knownCount；值为 0 另计 knownZeroCount；无标记的另计 knownImplicitCount |
| UNKNOWN | 值 null（显式 UNKNOWN 或无标记）且列为 NULL | 否 | unknownCount |
| LEGACY_UNCONFIRMED | 值 0（显式 LEGACY 或无标记）且列 = 0 | 否 | legacyUnconfirmedCount |
| INVALID | 标记非法/与值矛盾、knowledge 不是对象或含其他键、金额不是数字或为负/超限、列与文档不等 | 否 | invalidCount |

## 4. SQL 聚合与对账

一条语句、一个快照：

```sql
SELECT GROUPING(g.stage)=1, g.stage, count(*),
  coalesce(sum(g.amount) FILTER (WHERE g.class='KNOWN'),0)::numeric(20,2)::text,
  count(*) FILTER (WHERE g.class='KNOWN'), … 'UNKNOWN', 'LEGACY_UNCONFIRMED', 'INVALID'
FROM (SELECT CASE WHEN p.sales_stage IN (12 个编码) THEN p.sales_stage ELSE '' END AS stage,
             p.estimated_amount AS amount, <amountClassSQL> AS class, … FROM intake_projects p
      WHERE <projectScope + 基础筛选>) g
GROUP BY GROUPING SETS ((g.stage), ())
```

- 范围与筛选直接复用 G3-3A 的 `projectFilters()`（同一 `projectScope`）；无新权限、无新索引、无迁移。
- 金额只用数据库 numeric `SUM`，返回两位小数字符串；Go 只转发字符串，Vue 只按字符串加千位分隔（`amount.ts`，超过 2^53 的金额不丢位，Vitest 覆盖）。
- 非标准阶段的项目单独成组，返回 `unclassified` 与 `unclassifiedAmount`；12 个阶段 + 非标准组 = 全局（数量与金额）。
- 每组 `knownCount + unknownCount + legacyUnconfirmedCount + invalidCount = 项目数`。
- 查询次数：统计本身 1 条（`STAGE_SUMMARY_QUERIES rows0=1 rows500=1`）；HTTP 请求 2 次往返（含会话校验）。

## 7. 精度与一致性反证

**精度（`precision-and-classes`）。** 0、0.01、0.10、125000.25、99999999999.99、三个 0.01 重复相加、3 个 NULL、无标记 0、1.005（不一致→INVALID）、三条历史行（0、250.75、1000，其中一条为非标准阶段）。L5 结果：`knownTotal="100000125251.13"`、knownCount 9、knownZeroCount 1、knownImplicitCount 1、unknown 3、legacy 2、invalid 1，与十进制精确和一致；非标准组 1 个项目、`"1000.00"`；空阶段 `"0.00"` 且 knownCount 0。

**一致性（`consistency-through-lifecycle`）。** 创建后 → 编辑金额 → 同时改金额与阶段（L1→L2，原阶段归零）→ 旧版本 PATCH 409 与已知性矛盾的 PATCH 400（汇总不变）→ 提交（按“已提交/草稿”筛选口径随之变化）→ 退回改金额再提交 → `stage-change` L2→L3。每一步阶段金额、计数与 Go 参考一致。两个会话以同一版本并发推进阶段：一个 200、一个 409，汇总只反映成功的那一次。另一个销售持续写入期间连续读取 15 次统计，每次“各阶段 + 非标准 = 全局”都成立（单语句快照）。
