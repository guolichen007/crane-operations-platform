# 项目报备中心生产部署契约

本文件是 Baobei 生产部署唯一契约。永久分支 product/baobei-v1；不合并 main/R2。
S1B_PUBLIC_DEPLOY=NOT_AUTHORIZED；本轮仅实现代码、模板和本地验证，不执行发布、安装、启用 timer、签发证书或服务器操作。

## 端口与共享入口

BAOBEI_WEB_CONTAINER_PORT=8080；API_CONTAINER_PORT=8088。
流向固定为 shared ingress → baobei-web:8080 → baobei-api:8088。Web 保留 `listen 8080;`。
共享 ingress 单独加入 u-dao-baobei-frontend，Web 连接 frontend/internal，API 连接 internal/egress，PostgreSQL 仅 internal；没有生产 host port。
入口模板位于 deploy/baobei/ingress/，common 文件加载在 http 上下文一次，域名文件加载在同一 http 上下文。common 仅定义两个 Baobei 限流区。Baobei HTTP 与 HTTPS vhost 各自声明 Docker DNS resolver 127.0.0.11 和 5 秒超时。动态上游为 baobei-web:8080。
模板拒绝 upstream 的 80 端口；静态反证使用 `baobei-web:80(?!\d)`，不会误伤 8080，同时要求 upstream 精确为 8080。

宿主机 Baobei ACME 将 HTTP-01 token 写入 `/srv/u-dao/platform/ingress/acme-webroot/.well-known/acme-challenge/`。只有 baobei-web 只读绑定该 webroot 到 `/var/www/acme`。部署前应准备真实目录和 Web worker 可读的普通 challenge 文件，Compose 禁止自动创建缺失的源目录。Web 限定单段 base64url token、GET/HEAD，禁目录列表、符号链接、请求日志和缓存。

公网 TCP 80 的 challenge 请求由共享 ingress 保留 Host 和原路径代理到 `baobei-web:8080`，其余 HTTP 路径以 308 跳转 HTTPS。共享 ingress 复用现有 TLS 根挂载，从 `/etc/nginx/tls/baobei/` 加载 Baobei 证书；Baobei Web 仅挂配置和 challenge 目录。共享 ingress 无新增 ACME Volume，可在原容器接入 Baobei frontend 网络，经 `nginx -t` 后 reload。自动签发前，必须先用域名从公网 HTTP 请求宿主写入的验证 token 并核对响应体。

INGRESS_NEW_ACME_VOLUME_REQUIRED=NO，BAOBEI_WEB_ACME_MOUNT_READ_ONLY=YES，BAOBEI_WEB_NO_TLS_PRIVATE_KEY_MOUNT=YES。

## GHCR 发布及正式 manifest

唯一正式镜像名：ghcr.io/guolichen007/baobei-web、ghcr.io/guolichen007/baobei-api。
发布工作流仅监听 `release/baobei-publish-<完整40位小写十六进制SHA>` 分支的 push。实际执行要求官方仓库、新建 ref 事件、首次运行、事件 SHA、ref 后缀与 checkout HEAD 一致，以及该提交属于远端产品分支历史。最新同 SHA、同产品分支、同 Baobei CI workflow 的同一 attempt 八门都必须成功。普通产品 push 只触发 Baobei CI。

仓库管理员须在 GitHub Settings → Environments 提前创建 `baobei-ghcr-publish`。Required reviewers 使用直接指定的个人账号，启用 Prevent self-review，关闭管理员绕过。Deployment branches and tags 选 Selected branches and tags，仅配置一条 Branch 类型规则，值为此次获准的完整 release 分支名。直接指定账号可以通过公开 API 核对审批者 ID。

无写权限的 preflight Job 先核对 Environment、reviewer 和唯一 Branch 规则。发布 Job 引用该 Environment，由 GitHub 等待人工审批。Job 启动后重新核对设置，并读取当前 run 的审批记录，校验 Environment ID 和具名 reviewer 的同意记录。缺少规则、审批或可靠 API 证据时输出 `RELEASE_ENV_NOT_VERIFIED` 并停止。该方案使用公开只读 API，发布 Token 仅在发布 Job 授予 packages:write。

首次激活由负责人另行授权。选定含本工作流且已通过八门 CI 的产品 SHA，为它设置 Environment 分支规则，然后以该提交直接创建一次性远端 release ref。此 ref 只指向该提交，禁止附加改动、合并或打 Git tag。首次运行通过人工审批才能构建和推送。失败后的重试也需要新授权和新的创建事件，由负责人先清理原 release ref，再用同一 SHA 创建它，并重新审批。GitHub 的 rerun 因审批历史按 run 记录而被拒绝。

官方文档：[工作流触发事件](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows)、[Environment 保护](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments)、[分支策略 API](https://docs.github.com/en/rest/deployments/branch-policies)、[审批历史 API](https://docs.github.com/en/rest/actions/workflow-runs#get-the-review-history-for-a-workflow-run)。

发布使用每次运行唯一的 `sha-<完整SHA>-run-<runID>-<attempt>` 镜像 tag，不写 latest、不创建 Git tag。部署始终使用 name@sha256 registry manifest digest，不使用 tag 或本地 image ID。
两个镜像包含 revision/source OCI 标签。工作流构建 linux/amd64，临时 Docker config 以 GITHUB_TOKEN 经 stdin 登录，仅授予 contents:read/packages:write；第三方 action 固定完整 commit。构建 context 为 allowlist，不包含 .env、secret、客户资料、OIDC secret、数据库密码或 production env。运行时 secret 只从外部文件挂载。

发布后分别读取 registry manifest digest，按固定仓库名@digest 重新 pull，inspect 必须同时匹配 RepoDigests、revision=source_sha、source=https://github.com/guolichen007/crane-operations-platform。另用全新无凭据 Docker config 再次 pull 验证 Public。
只有全部成功才原子写出 artifact `deployment-manifest.json`：source_sha、web_registry_ref/digest、api_registry_ref/digest、openapi_hash、transfer_hash、schema_version、created_at、registry_published=true，另含 public_pull_verified、platform 和 CI run ID。失败会清除旧 manifest，不产生成功 artifact；所有状态均保持 READY_FOR_PRODUCTION=NO、S1B_PUBLIC_DEPLOY=NOT_AUTHORIZED。

现有 `local-private/baobei/release/<SHA>/manifest.json` 只属开发证据，digest_kind=local_image_id、registry_published=false；不可用于生产。正式 registry artifact 位于独立 registry-release 目录，必须从成功的指定发布运行取得并校验，不可把两个 manifest 混用。部署前需重新核对远端发布 artifact/源 SHA/契约 hash/schema 与镜像 digest，不能仅信任可手改的本地 JSON。

## Package 可见性

首次获准发布会先推送两个镜像并验证其 registry digest 和 OCI 标签，再执行两次匿名回拉。若初次创建的 Package 是 Private，匿名回拉失败将输出 `PUBLIC_PULL_NOT_VERIFIED`，工作流失败，正式部署清单缺席。负责人将两个 Package 设为 Public 后，可按上面的新建 ref 和审批流程另行授权重试。
生产从已验证的 Public registry digest 拉取。带写权限的发布 Token 仅用于发布 Job。

### 生产角色与执行顺序

| 身份 | 用途与权限 |
| --- | --- |
| `baobei_bootstrap` | PostgreSQL 初始化管理员。其密码文件仅供 PostgreSQL。 |
| `baobei_migrator` | 一次性 `maintenance migrate`。拥有迁移创建的表与函数，可在 public schema 执行 DDL。 |
| `baobei_runtime` | 常驻 API 业务连接和 `maintenance protection-sweep`。读取基础身份与 capability，可按列记录登录时间。 |
| `baobei_staff_api` | 常驻 API 的企业会话签发和人员治理连接。可按列写入人员状态与项目归属，维护独立人员会话证明、审计和 Outbox。 |
| `baobei_maintenance` | 一次性 `maintenance identity-apply` 和 `maintenance staff-provision --once`。处理旧身份清单和 BB-B3 审批回执。 |

在后续获准部署时，按以下顺序操作。

1. 使用独立空卷启动 PostgreSQL。Compose 将 `deploy/baobei/db/initialize.sql` 和 `deploy/baobei/db/staff-role.sql` 依序只读挂入初始化目录，安装 pg_trgm、撤销 PUBLIC 访问并创建四个受限登录。管理员在本地 psql 对各角色分别使用 `\password <角色>` 设置独立 SCRAM 密码。已有 BB-B2 分权卷在停 API、备份后，先由初始化管理员连接专用 `baobei` 库执行 `staff-role.sql` 并设置人员角色密码，再迁移。通过受控文件提供相应 DSN，地址使用 internal 网络上的 `baobei-postgres`。按 UID 10001 的只读需要配置运行凭据，特权 DSN 独立保管。
2. 用部署清单中的 API digest 在 internal 网络运行一次性迁移容器。迁移在一笔事务内应用未执行的脚本、校验台账、授予业务和维护角色所需权限。已部署系统升级时先备份并停止常驻 API，再使用获批的新镜像执行迁移。
3. 使用独立维护 DSN 和 root-only 审批清单运行身份命令，先 dry-run。完成后启动常驻 API，挂载 `runtime_database_url`、`staff_database_url` 和 `oidc_client_secret`。两个 DSN 指向同一数据库、主机及端口，并各自以规定角色登录。API 只读核对迁移版本及每个文件的 SHA256，缺失、落后、多余或 checksum 错误都会拒绝启动。

在 Linux 主机上，经过批准后可按以下模板执行一次性容器。变量由负责人设置为独立只读凭据文件的绝对路径与已验证的 API digest。迁移 DSN 文件须让镜像默认 UID 10001 读取，维护 DSN 与清单由 root 读取。

```bash
docker run --rm --read-only --network u-dao-baobei-internal \
  --security-opt no-new-privileges --env APP_ENV=production \
  --env DATABASE_URL_FILE=/run/secrets/db_url \
  --mount "type=bind,src=$MIGRATOR_DSN_FILE,dst=/run/secrets/db_url,readonly" \
  "$BAOBEI_API_IMAGE" maintenance migrate

docker run --rm --read-only --user 0:0 --network u-dao-baobei-internal \
  --security-opt no-new-privileges --env APP_ENV=production \
  --env DATABASE_URL_FILE=/run/secrets/db_url \
  --mount "type=bind,src=$MAINTENANCE_DSN_FILE,dst=/run/secrets/db_url,readonly" \
  --mount "type=bind,src=$APPROVED_IDENTITY_FILE,dst=/run/baobei/identity.json,readonly" \
  "$BAOBEI_API_IMAGE" maintenance identity-apply --file /run/baobei/identity.json \
  --operator "$APPROVED_OPERATOR_ID" --dry-run
```

00001 和 00002 文件及校验和保持原样。00003 只向前迁移，原有账号的 subject、团队和项目关联保留，原有销售能力全部保留，登录状态按已有 active 值回填。若发现已有旧版单账户卷，先停在迁移前，另行审查备份、角色和对象所有权移交方案。PostgreSQL 的初始化目录只在空卷执行。

## 身份初始化与证书

Keycloak 配置以 Keycloak生产配置契约.md 为准。生产不手写 SQL 建用户，不允许首次登录自动建 app_users。

BB-B3 页面管理过的人员通过受控 `staff-provision` 继续处理，`identity-apply` 遇到这些账号会拒绝整个清单。回执、审批和激活流程见 [Keycloak 生产配置契约](Keycloak生产配置契约.md)。
身份变更通过以下 CLI，输入限 Linux root:root、0600/0400、普通文件、无 symlink、最大 1 MiB，审批编号和 operator evidence ID 必填。JSON 严格拒绝未知字段、重复 key、重复 subject/团队 ID；真实资料只放仓库外或忽略目录。

```json
{"approvalReference":"SYNTHETIC-APPROVAL-001","teams":[{"id":"66666666-6666-4666-8666-666666666666","name":"Synthetic Team"}],"users":[{"subject":"77777777-7777-4777-8777-777777777777","displayName":"Synthetic User","role":"baobei_sales","team":"66666666-6666-4666-8666-666666666666","active":true}]}
```

subject 必须为真实 Keycloak UUID/sub；上例全部 synthetic。销售/主管必须关联已存在或本次显式创建的 team；总监/管理员 team 必须为空字符串。active 必填，停用显式 active=false；遗漏用户不会被删或停用，不删除团队/用户，不根据 Keycloak role 自动审批 Team/Role。

```text
baobei maintenance identity-apply --file /run/baobei/identity.json --operator APPROVED_OPERATOR_ID --dry-run
baobei maintenance identity-apply --file /run/baobei/identity.json --operator APPROVED_OPERATOR_ID
```

一次性容器使用上面的独立维护 DSN。身份 CLI 在初始化 OIDC 前返回。
所有团队、用户、会话撤销和审计在单一事务内，dry-run 整体 rollback；重复执行无状态变化、不重复审计。角色/团队/状态/姓名变更撤销对应会话，登录建会话与导入锁互斥，防止旧 token 并发授权。审计记录 operator、审批编号、manifest SHA256、计数；输出只有计数、hash 和 dry_run，不含姓名、UUID、token/password 或原始输入。审批文件与审计须由负责人核对，CLI 不取代组织审批。

证书契约见 deploy/baobei/cert/README.md；独立路径/单位、HTTP-01、固定 acme.sh 3.1.6、健康探测/回滚/recovery journal。TrustAsia bootstrap-* 仅用于人工启动/紧急回退，不由自动流程覆盖。

## 验证与授权边界

维持原八门架构，新增生产反证、mock 发布、真实临时密码学与 fake 网络的 ACME 事务测试、identity CLI/数据库/OIDC 反证。发布测试从不 login/push 真实 registry；证书测试不访问 CA、真实域名或宿主生产目录。
本轮完成只说明代码/模板/CI 可审查。真实发布、GHCR 可见性设置、身份应用、ACME 安装/签发/adopt/timer、生产部署均需后续明确授权。
