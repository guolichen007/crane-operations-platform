## 1. 原实现查询流程

`GET /projects/{id}/duplicate-comparison`（改造前，N = 相关候选数）：

```text
会话校验 user()                         1
主项目 get()                            1
comparison(): 候选 case 列表            1
  for 每个候选:
    get(candidate)                      N
    evidenceGrade(candidate)  (仅可读)  ≤N
projectHints(): 审核资格事实             1
合计                                    4 + 2N（可读候选全部时）
```

`POST /projects/{id}/duplicate-decisions`（改造前）：会话、BEGIN、beginBusiness（身份共享锁 + 会话复核）、727102、`relatedReviewProjects`（1 条 FOR UPDATE + 逐个 `get` N+1 条）、主项目 FOR UPDATE、`reviewIndependence`、逐候选 `candidateIndependence` N 条、事务内 `comparison()` 1+2N 条、逐候选 `evidenceGrade` N 条、写入、审计与 COMMIT。实测 16 + 5N（BEGIN/COMMIT 计入）。

改造后：

```text
GET 对比: 会话 1 + 主项目 1 + comparison 集合查询 1 + 审核资格事实 1 = 4（常量）
POST 裁决: …727102 → relatedReviewProjects（FOR UPDATE 语句不变 + 1 条 ANY 读取）→ 主项目 FOR UPDATE
          → reviewIndependence → loadCandidateFacts 1 条 → comparison 1 条 → 写入与审计 = 17（常量）
```

## 3. 事务锁顺序对照

| 步骤 | 改造前 | 改造后 |
| --- | --- | --- |
| 1 | `pg_advisory_xact_lock_shared(727105)` 身份共享锁 | 不变 |
| 2 | `pg_advisory_xact_lock(727102)` 提交/裁决全局锁 | 不变 |
| 3 | `SELECT id … ORDER BY id FOR UPDATE`（主项目 + 本轮候选 + 已裁决候选，UUID 升序） | **同一条 SQL 文本不变** |
| 4 | 逐个 `get()` 读取已锁行 | 一条 `WHERE p.id=ANY($1) ORDER BY p.id` 读取已锁行（不再取锁） |
| 5 | 主项目 `get(…, FOR UPDATE)`（已持有，重入） | 不变 |
| 6 | 逐个候选独立性、证据等级 | 一条 `loadCandidateFacts`（无锁读，行已锁） |

没有新增、删除或重排任何锁；步骤 4、6 只读已在本事务加锁的行，不可能引入新的等待环。候选判定仍按 UUID 升序逐个评估，第一个不可读的候选返回 `REVIEW_RELATED_PROJECT_RESTRICTED`、第一个有参与冲突的候选返回 `REVIEW_CONFLICT`，与改造前首个失败候选决定原因码的行为一致。

**最小优化方案（提案，未实施）。** 方案 A（推荐，零迁移）：在审核队列的只读快照事务和首页汇总查询前执行 `SET LOCAL jit = off`，仅影响这两条交互式 OLTP 查询，不改变 SQL 语义与结果。方案 B：在部署配置中提高 `jit_above_cost`（例如 10⁷）或关闭 `jit`，影响全库，需要运维确认并复核 Compose/备份恢复门禁。方案 C（G3-3 时考虑）：把 `reviewableSQL` 的相关子查询改为预聚合 CTE，降低估算代价并减少每项目的子计划，属于谓词重写，需要重新跑 1296 矩阵与队列等价测试。三者都不需要新索引；本批未发现缺失索引：分页与计数的主过滤走 `project_submissions` 顺扫 + `intake_projects_pkey`，子计划走 `project_submissions_pkey`、`participation_actor_idx`、`duplicate_project_idx`，`ownership_history` 为 hashed SubPlan。
