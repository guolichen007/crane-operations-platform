## 1. P1-A 金额汇总上限

**复现（PG18 真实 SQL 与 API，合成数据）。** 10,000 个项目，每个 `estimated_amount = 100000000000000.00`，文档金额一致，knowledge = KNOWN，期望合计 `1000000000000000000.00`（19 位整数）。

| 实现 | 结果 |
| --- | --- |
| 修复前表达式 `coalesce(sum(...),0)::numeric(20,2)::text` | SQLSTATE `22003` numeric field overflow |
| 修复前 `GET /api/v1/stage-summary`（主管） | HTTP **503** `SERVICE_UNAVAILABLE`，所有角色的统计都不可用 |
| 修复后 | HTTP 200，`knownTotal="1000000000000000000.00"`、`knownCount=10000`，报价阶段同值 |

原始记录：`local-private/baobei/g33br1/r1-overflow-before.txt`、`r1-overflow-after.txt`。

**修复（`stage_summary.go`，4 行）。** 改为 `round(coalesce(sum(...),0),2)::text`：PostgreSQL `numeric` 不设精度时没有位数上限，`round(…,2)` 只固定两位小数的文本形式（各加数本来就是 `numeric(18,2)`，不会产生舍入）。仍是同一条 SQL、同一快照；没有改为 float64 或 bigint。

## 2. P1-B 金额写入精度

**修复前复现（真实 API，`r1-write-before.txt`）。**

| 请求原文 | HTTP | 列 | 文档 | 问题 |
| --- | --- | --- | --- | --- |
| 0.125 | 200 | 0.13 | 0.125 | 服务端隐式舍入，两处不一致 |
| 100.005 | 200 | 100.01 | 100.005 | 同上 |
| 12345678.9999 | 200 | 12345679.00 | 12345678.9999 | 同上（统计判为 INVALID） |
| 90071992547409.91 | 200 | 90071992547409.90 | 90071992547409.9 | float64 静默丢 1 分，两处“一致”地错 |
| 99999999999999.99 | 200 | 99999999999999.98 | 99999999999999.98 | 同上 |
| 1e3 | 200 | 1000.00 | 1000 | 接受指数写法 |

**修复前浏览器（`r1-browser-before.txt`）。** 输入 `123.456`，浏览器原样发送、服务端 200，列存 123.46；输入 `90071992547409.91`，浏览器发送 `90071992547409.9`（JS Number 已丢分）、服务端 200。另外，`NumberField` 在输入非法时直接 `return`，不更新模型，自动保存会把**之前的合法金额**再次发出去，用户看到的是非法文本。

**方案选择。** 现有 `*float64` 契约下可以证明：所有不超过 9,999,999,999,999.99 的分值（随机 1,000 万个 + 临界 100 万个全部通过）以及所有不超过 1e14 的整元值经 float64 往返后十进制不变；只有 1e13 以上带分的部分值（抽样约 11.8%）无法精确表示。因此选择**方案 A：无法无损存储的输入明确拒绝**，不改数据类型、不缩小已批准范围：

| | A（已实施）：拒绝不可精确表示的输入 | B（未实施）：新增可选精确字符串字段 |
| --- | --- | --- |
| OpenAPI | 字段类型不变，补充规则说明 | 新增 `estimatedAmountDecimal`，需要两字段互斥规则 |
| 旧客户端 | 合法两位小数照常；不合法输入从“静默改值”变为 400 | 不受影响 |
| 已有草稿 | 金额不变；只在再次保存时校验 | 同 A |
| G1 历史数据 | 不改；只读统计照旧 | 不改 |
| 剩余限制 | 1e13 以上带分的金额需改为整元或较小金额 | 可完整支持 |

B 在需要录入 1e13 元以上精确到分的金额时再评审。

**服务端（最终验证者，`amount_input.go`）。** `POST /projects` 与 `PATCH /projects/{id}` 在 float64 解码之前读取原始 JSON 数值 token 并检查：普通十进制写法（无指数、非字符串）、0–1e14、最多两位小数（多余位只能是 0）、float64 最短表示与原值十进制相等。任一不满足返回 400 `INVALID_INPUT`，消息说明是格式、范围、精度还是无法精确保存。校验发生在任何写入之前（PATCH 在已加锁的事务内，被拒时整笔回滚）。`submit`、`stage-change`、跟进等不带金额输入的接口不经过该校验。G1 已知性规则在其后照常执行。

**修复后矩阵（`TestDatabaseG33BR1AmountInput`，真实 API，`r1-input-after.md`）。** 每个接受的请求断言“请求原文 = 数据库列 = 文档金额”（十进制）且统计类别正确；每个拒绝的请求断言项目数、版本和、审计、参与、跟进、关系方、设备、创建回执与全部金额列完全不变。

| 请求 | 结果 |
| --- | --- |
| null（无标记 / UNKNOWN） | 200，NULL / null，UNKNOWN |
| 0 + KNOWN / 0 无标记 / 0 + LEGACY | 200，均为 0；分别为 KNOWN、LEGACY_UNCONFIRMED、LEGACY_UNCONFIRMED |
| 0.01、0.10、125000.25、9999999999999.99、90071992547409.90、1e14（两种写法） | 200，三处十进制相等，KNOWN |
| 125000.25 无标记（旧客户端） | 200，KNOWN |
| 0.125、100.005、12345678.9999 | 400“最多保留两位小数” |
| 90071992547409.91、99999999999999.99 | 400“无法精确保存到分” |
| 100000000000000.01、-1 | 400“超出允许范围” |
| 1e3、"125000.25" | 400“格式不正确” |
| 5 + UNKNOWN | 400“数值及已知性标记不一致”（G1 规则不变） |

编辑：合法金额改为另一合法金额成功；123.456、90071992547409.91、-5、1e2 的 PATCH 全部 400 且无任何写入；两个会话同版本编辑，一个 200、一个 409，金额为胜出者的值；改为 UNKNOWN 再改为 KNOWN 0，两者仍区分。纯函数测试 `TestCheckAmountToken` 覆盖 25 种原文。

**前端。**

- `numeric.ts` 新增 `parseMoney()`，与服务端规则一致：千位逗号可省略，用 BigInt 按分比较范围，检查 JS Number 实际会发送的数值是否仍是同一分值。Vitest 覆盖合法与 11 种非法输入。
- `NumberField`（金额使用 `money` 模式）：非法时**原文保留**在输入框，下方显示具体原因（`role="alert"`），并向表单报告“无效”。打开项目时若已存金额本身不合格（R1 前写入的多位小数），立即显示原值与提示。离开该步骤或移除设备行时撤销无效标记（模型仍是上一个合法值）。
- `Wizard`：存在无效数值时“保存草稿”与“提交”禁用并说明原因，自动保存跳过，状态显示“数值有误，未保存”，`save()` 在发送前再次拦截。
- 浏览器反证（`g33br1-amount-input.spec.ts`，桌面与 390）：保存 125000.25 后依次输入 123.456、90071992547409.91、100000000000000.01、-5，每次原文保留、提示正确、按钮禁用；改为 90071992547409.90 后，期间捕获到的所有写请求都只携带新值（从未发出旧值），服务端精确保存；清空后为 UNKNOWN 而非 0；直接用 API 绕过浏览器 PATCH 0.125 被 400 拒绝且版本不变。修复前的代码上这两个用例都失败。G2 的创建、409 差异面板、三向合并与历史 0 确认用例全部通过。

## 3. 历史数据保护

- 本批没有修改任何金额、文档、knowledge 或迁移。`invalidCount`、`legacyUnconfirmedCount`、`knownImplicitCount` 的判定与 G3-3B 完全相同（25 例法证全表 Go = SQL 继续通过）。

- 不提供批量改写；历史异常的集中人工复核入口仅作为后续需求（见第 6 节）。
