基线 `e5186eb`（CI Run 43154286068，Attempt 1：执行时 7 项已 SUCCESS，e2e 仍在运行；负责人指示跳过 e2e 核对）。本批只修复 R1-E 独立审查发现的账号一致性和迁移校验风险，不扩大业务需求。生产 Keycloak、生产数据库和运行容器均未操作（PRODUCTION_MUTATION=NONE）。

## 1. 身份迁移校验（deploy/baobei/identity-migration.py）

R1-E 的问题：verify 只比对部分字段，登录名、员工编号未逐一核对；导入用 `ifResourceExists=SKIP`，同 UUID 不同内容会被静默跳过；`links` 不经校验即可输出；`oldUsername`、`keycloakOnly.username` 未遮蔽。

修复后：

- **业务导出与计划交叉核对**：计划中的员工编号、业务 subject、角色、状态必须与私有业务导出逐行一致；计划缺行、重复员工编号、改写新 UUID、把不可导入的行（缺手机号、未绑定、合成身份）标为批准，一律拒绝。
- **逐字段核对新 Realm**：新 UUID（UUIDv5(业务 subject)）、`baobei_staff_id`、`baobei_subject`、登录名（必须严格等于批准手机号的 11 位，`+86…` 不算同一登录名）、报备角色（归档只保留历史、不带角色）、无 Crane/Realm 角色与组、无凭据、启用状态（停用与归档在任何阶段都不得启用；在职成员只有在受控启用步骤后才允许启用）。
- **不允许多余或重复**：计划外账号、重复 UUID、重复登录名、多个账号映射到同一员工或同一业务 subject、未批准成员在新 Realm 中已有账号，都判失败。
- **导入**：先读取新 Realm 现状；存在同 UUID / 同登录名 / 同员工编号但内容不同的账号即拒绝，不写导入文件。导入文件改为 `ifResourceExists=FAIL`，只以新私有文件（0600，不覆盖已有文件）写出；内容完全一致的已有账号单独列为 `alreadyPresentIdentical`，SKIP 不再作为接受身份冲突的证据。
- **links**：先执行完整 verify，失败时不输出任何 SQL；成功时输出单个事务，每行插入前在数据库内再校验员工编号、subject、角色。
- **手机号遮蔽**：所有终端输出经过守卫，出现完整手机号或 11 位登录名即拒绝打印；`oldUsername`、`keycloakOnly.username` 中 7 位以上数字段遮蔽。含原始手机号的业务导出必须是私有文件（组/其他用户可读即拒绝）。原始手机号只存在于服务器上权限受控的导出文件中，不进入 Git、CI 日志或报告。

反证（`tests/baobei/identity`，CI contract 门执行，26 项）：错误手机号、`+86` 登录名、错误员工编号（属性与计划两种）、错误业务 subject、角色不一致、多余角色、Crane 角色或组、计划内改角色、重复 UUID、两个账号映射同一成员、意外启用、额外账号、存在凭据、缺失账号、计划缺行、不可导入行被批准、改写新 UUID、未批准成员已在新 Realm、导入冲突（同 UUID 不同登录名 / 不同归属 / 登录名被占）、不覆盖已有文件、遮蔽与私有文件检查。另做变异验证：逐个删除工具中的每项检查，对应测试均失败。

## 2. 账号操作可恢复（迁移 00007，不修改 00006）

R1-E 的问题：`account_operations` 在 Keycloak 调用期间保持 STARTED；进程被杀、补偿失败或 `finishAccountOp()` 写库失败（错误被忽略）时，成员永久卡在“处理中”，且唯一索引阻止任何后续操作。

00007 增加：`step`（OPENED、KC_CREATE、CREDENTIAL、ROLE、BOUND、ENABLE、KC_DISABLE、KC_USERNAME、KC_PASSWORD、FINAL）、`lease_token` / `lease_expires_at`（租约 2 分钟）、`attempts`、`request_hash`（请求指纹）、`reason`、`target_login` / `previous_login`、`created_user`、状态 `REVIEW`（待核对），以及账号状态 `REVIEW`。唯一约束改为：每名成员最多一项未解决操作（STARTED 或 REVIEW），每个登录手机号最多一项未解决操作。00006 遗留的 STARTED 行在迁移时立即交给恢复流程。staff_api 只新增步进与租约列的 UPDATE 权限，请求字段只能 INSERT；runtime 没有任何新增权限（`TestDatabaseProductionPrivileges` 通过）。

**执行顺序与一致性契约**：

1. 操作行（含请求指纹与目标登录名）先提交，再调用 Keycloak；每一步先记录步骤再调用。
2. 最终的业务状态、审计记录与操作 DONE 在同一事务中提交；提交成功后才返回成功和一次性密码。
3. 写库失败不再被忽略：返回 `ACCOUNT_RESULT_PENDING`（带操作编号），操作保持 STARTED，租约到期后由恢复流程接管。
4. 无法确认 Keycloak 与业务是否一致时，操作和账号进入 REVIEW：成员所有会话结束，登录入口拒绝 CREATING 与 REVIEW，管理员点击“核对账号状态”后才能继续。
5. 一次性临时密码只在内存中，不写入任何表、审计或日志。

**恢复规则**（API 启动时及每分钟执行一次，管理员也可手动“核对”）：先读 Keycloak 当前状态，再决定。

| 操作 | Keycloak 显示 | 结果 |
| --- | --- | --- |
| 开通 | 任意中断 | 删除本次创建的用户（成员原有的停用用户只停用），解除绑定，记为开通失败，可重新开通并得到新密码；初始密码从未送达，因此不会完成 |
| 开通 | 记录的用户不属于该成员 | 不触碰，待核对 |
| 重置密码 | 任意中断 | 不重放；结束该成员会话、要求改密、记为“结果未送达”，管理员重新重置 |
| 更换手机号 | 已是新号 / 仍是旧号 / 其他 | 补完数据库 / 关闭且不变更 / 待核对 |
| 停用 | 仍启用 | 再次停用并完成；仍无法确认则待核对（报备中心已先停止该成员访问） |
| 恢复 / 同步角色 | 已启用且恰好一个正确角色 / 其他 | 补完 / 重新停用登录，避免越权 |

**幂等**：同一幂等键必须对应同一员工、同一操作、同一手机号和原因，否则返回 `ACCOUNT_IDEMPOTENCY_MISMATCH`；已完成的请求重放时不再显示密码；失败的请求不会被同一键重放。成员资料编辑不能再绕过账号服务修改已开通账号的手机号（`STAFF_PHONE_ACCOUNT_BOUND`）。

**故障注入**（`r1f_account_recovery_test.go`，真实 PostgreSQL 事务，9 组）：

- Keycloak 创建后崩溃、启用后崩溃。
- 记录步骤失败、绑定事务失败、最终事务失败。
- Keycloak 超时但实际已创建，包括随后的查询也失败的情况。
- 补偿删除失败，以及在服务未恢复时进行核对。
- 重置密码成功但响应丢失；重置后崩溃，重启后不重复重置。
- 更换手机号后数据库失败，由恢复补完；崩溃发生在调用 Keycloak 之前；新号被他人占用时把用户名改回。
- 恢复登录后业务写入失败；停用时 Keycloak 无法确认。
- 同一幂等键对应不同员工、不同操作或不同原因；并发开通。
- 登录名属于其他成员时拒绝接管；同一登录名不能同时有两项未完成操作。
- 00006 遗留的 STARTED 行能被恢复。
- 编辑资料不能修改已开通账号的登录手机号。

所有用例都确认：不能冒用他人身份、不会无意提权、不留下管理员无法继续处理的状态、临时密码不入库。另做变异验证，分别去掉以下任一保护，至少一个用例失败：登录门禁、重置不重放、写库错误上报、恢复时撤销开通、补偿失败转待核对、请求指纹。

## 3. 账号页面

页面布局不变，只改动以下几处：

- 列表和详情的状态显示“处理中”和“待核对”，这两种状态都不再显示“可登录”。
- 详情页显示最近一次未完成操作的原因，用中文说明。
- 待核对或处理中时，账号相关按钮只保留“核对账号状态”；失败后显示原因和“开通登录账号”重试按钮。
- 账号操作失败时，弹窗和已填内容保留，背后的成员状态刷新为服务端的实际状态。
- 初始密码弹窗中明确写出“关闭后无法再次查看”。关闭后再提示可以通过“重置密码”生成新的初始密码。
- 已开通账号的成员在编辑资料时，手机号为只读，提示改用“更换登录手机号”。
