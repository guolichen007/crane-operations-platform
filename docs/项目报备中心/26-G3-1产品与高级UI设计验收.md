## 2. 当前系统审查（真实页面）

范围：销售、主管、总监、管理员 × 工作台、项目列表、管道、待跟进、详情、新建（仅销售/管理员）、审核与重复（仅主管/总监/管理员）× 1440/1366/768/390，空数据与有数据。

**数据来源与性能。** 首页只调用 `/api/v1/me` 与 `/api/v1/workspace-summary`；详情只调用 `/api/v1/me` 与 `/api/v1/projects/{id}`。各页 `networkidle` 加载中位约 0.55s（本机，含 vite preview 静态服务），无明显差异。

## 4. 四角色信息架构

原则：首屏回答“我现在该做什么”；每个数字都能点开同口径列表；角色只看到自己范围内的数据；不为不存在的接口画可点击入口。

| 角色 | 首屏（从上到下） | 次级区域 | 导航（服务端能力驱动，沿用 G2） |
| --- | --- | --- | --- |
| 销售 | ① 快速报备主按钮 ② “今天要做”：逾期跟进 + 今日到期 + 被退回待补（列表，非数字墙） ③ 草稿续填（最近 3 个） | 本周日程时间线；我的项目阶段分布（G3-3 真实接口前只显示数量，不画漏斗） | 工作台、待跟进、我的报备、项目管道、统计 |
| 主管 | ① “我可独立审核”队列（前 5 条 + 等待时长 + 进入审核）② 本组逾期跟进 ③ 不能由我审核的待审（原因分组：我参与过/跨组候选/证据待核验） | 团队成员负载（每人：在办、逾期、7 天到期）——需新接口 G3-4；待交接项目 | 工作台、待跟进、团队项目、管道、报备审核、重复处理、统计、团队成员 |
| 总监 | ① 跨组重复风险队列（只有总监能处理）② 阶段分布与已知金额/未知数量（G3-3）③ 保护期风险与逾期 | 团队对比（G3-3/G3-4）；可独立审核数 | 同主管，范围为全部已分配 |
| 管理员 | ① 待分配草稿（含保管人、创建时长、一键指派）② 合法的独立审核 ③ 人员治理异常（待开通、同步失败、停用后有在办项目） | 全局业务概览（与总监同口径，含待分配） | 工作台、待跟进、全部项目、待分配草稿、管道、审核、重复、统计、人员、团队 |

**项目中心。** 一个列表组件、三种视图：表格（桌面默认）、卡片（≤700px 默认）、管道。范围标签与统计时间固定显示。每行/卡片固定四个信号：状态（报备）、阶段（销售）、负责人（或“待分配”）、下一步（日期+状态点：逾期红/已安排蓝/未安排灰）。

**详情。** 首屏三段：标题行（编号、名称、状态、负责人、主操作）；阶段路径条（当前阶段高亮、本阶段待补字段）；“下一步”卡片（下一步事项、下次跟进、最近一次跟进）。下方保留六区页签。

**排版**：中文优先 HarmonyOS Sans SC / PingFang SC / 微软雅黑，数字 `tabular-nums`。字号阶梯 12/13/14/15（正文）/18/22/26/34（关键计数）。行高正文 1.6、标题 1.35。

**间距与形状**：4 的倍数（4/8/12/16/20/24/32/40）；圆角统一 6px（按钮、输入、卡片），胶囊状态标签 999px；阴影只用于浮层（弹窗/抽屉）`0 20px 70px #15243b26`，卡片用 1px 边框不加阴影。

**表格**：行高 48（紧凑 40），表头 13px `--ink-3`，数字右对齐，状态用标签+文字（不只靠颜色）。

**状态规范**：Loading（骨架行，`aria-busy`）、Empty（说明+唯一主操作）、Error（原因+重试，保留输入）、401（回登录并保留回跳）、403（固定原因码文案）、404（不泄露存在性）、409（三向合并面板）、离线（顶部条+禁用写操作）。

## 6. 跨组重复候选隐私 ADR 提案（待负责人裁决）

**现状（真实 HTTP 探针，本批未改代码）。** 本组主管请求一个与跨组隐藏项目重复的报备：

- `GET /projects/{id}/duplicate-comparison` 返回该 case 的 `id`（case ID）、`score`=85、`risk`、`signals`（“相同客户或别名/相同位置/相同设备类型及数量/需求相同”）、`decision`、`restricted=true`；不返回候选项目 ID、正文或 `evidenceGrade`。
- `GET /projects/{id}/duplicates` 返回 `score`、`risk`、`signals`、`region`（省/市）、`createdAt`、`salesStage`、`message`；不返回 `candidateId`、`projectName`。
- 总监两接口都得到完整候选。

即：不可读候选的**存在、相似度、匹配维度、地区、阶段、创建时间与裁决状态**目前对本组主管可见。这些字段已经能让主管推断“其他团队在同一客户、同一地区、某阶段有项目”。前端 `Reviews.vue` 在“需总监处理”提示前也显示这些元数据。

**提案白名单（不可读候选，主管视角）**

| 字段 | 建议 | 理由 |
| --- | --- | --- |
| 是否存在疑似重复 | 显示 | 主管需要知道本报备不能由自己完成，需升级 |
| 不可读候选数量 | 显示（仅数量） | 用于“需总监处理 N 个跨组候选”提示 |
| `risk`（WARN/HIGH） | 显示 | 决定升级紧迫度，粒度粗 |
| `score` | 隐藏 | 精确分数可逐次比对推断信号组合 |
| `signals` | 隐藏 | 直接泄露客户/位置/设备/需求维度 |
| `region`、`createdAt`、`salesStage` | 隐藏 | 直接泄露其他团队项目的地区与进度 |
| `decision` | 只在已裁决时显示“已由总监处理” | 不暴露未决状态细节 |
| case ID | 保留（不透明） | 主管不能用它操作（服务端已拒绝），用于升级引用；如负责人要求可改为不返回 |
| `candidateId`、`evidenceGrade`、历史候选计数 | 不返回（现状已如此，G3-0 已修计数） | — |

服务端在 `comparison()` 与 `redact()` 返回层按此脱敏，不依赖前端隐藏；`/duplicate-checks`（创建时预检）对销售的现有脱敏同样纳入审查。**未经负责人批准不改变现状。** 批准后在 G3-2 实施并以真实 HTTP 负例证明两种隐藏候选状态下主管响应逐字节相同（除 case ID）。

| --- | --- | --- | --- | --- |
| 1 | 3 | 1 | 6 / 1.10ms / 1.59ms | 6 / 1.11ms / 1.48ms |

## 9. 三条关键流程

**A 销售报备与跟进（现有接口全部可用）。** 新建（`POST /projects`，带创建意图键）→ 四步补充（`PATCH /projects/{id}`，自动保存串行、409 三向合并）→ 提交（`POST …/submit`，服务端重查重）→ 详情查看状态（`GET /projects/{id}`）→ 记录跟进（`POST …/activities`）。错误：401 回登录保留回跳；403 显示原因码；409 合并面板；503/断网保留输入可重试。审计：`project.create`/`edit`/`submit`/`activity.create`。必须保留的反证：g2-create、g2r1-merge、flow。

**B 管理审核。** 待审列表（G3-2：`GET /reviews?eligibility=reviewable`）→ 打开对比（`GET …/duplicate-comparison`，G3-2 批量化）→ 资格提示（`review` 三项）→ 填原因 → `POST …/approve|return|reject|duplicate-decisions`（事务内重验独立性、版本、历史候选确认）→ 列表刷新且首页计数同步减少。审计：`review.*`、`duplicate.*` 含候选证据等级。反证：自审 403、历史候选未确认 409、并发版本 409、跨组不可裁决。

**C 跨组受限。** 本组主管打开含跨组候选的报备 → 只见第 6 节白名单字段与“需总监处理（N 个）”→ 审核/裁决按钮禁用并显示 `REVIEW_RELATED_PROJECT_RESTRICTED` 文案 → 直接 POST 返回 403 → 总监在同一报备看到完整候选并处理。反证：主管响应在两种隐藏候选状态下一致（G3-0 已证计数；G3-2 扩展到全部字段）。

## 10. G3-2 审核治理实施设计（待授权，不在本批实施）

**接口契约。**

- `GET /api/v1/reviews?kind=pending|duplicates|protection&eligibility=reviewable|blocked|all&page&pageSize&sort=waiting|updated`：服务端在列表 SQL 中复用 `reviewableSQL`（reviewable）或其否定（blocked），返回 `{items, total, asOf, counts:{reviewable, blocked, all}}`；blocked 项附 `review.reasonCode`。未知取值 400。首页 `reviewable` 卡片跳转 `eligibility=reviewable`。
- `GET /projects/{id}/duplicate-comparison`：一次集合查询取全部候选（`WHERE id = ANY(...)`），同一查询内计算 `primaryCompleteSQL` 证据等级与 `projectScope` 可读性，按第 6 节白名单在服务端裁剪不可读候选。目标查询数为常量（≤ 6），与候选数无关。
- 审核 POST：`relatedReviewProjects` 已一次加锁读取全部候选；`candidateIndependence` 与 `evidenceGrade` 改为对已加锁 ID 集合的一次查询，保留锁顺序（身份锁 → 727102 → UUID 升序行锁）与全部拒绝语义。

**反证测试（真实 PostgreSQL + HTTP）。**

1. 构造 reviewable=3、reviewQueue=10（其中 4 项本人参与、2 项跨组候选、1 项历史证据缺失）：首页数、`eligibility=reviewable` 的 total、逐项 `actions.approve|duplicate-decisions` 允许数三者相等；blocked 列表的原因码分布正确。
2. 分页末端与排序稳定：1,001 条待审，翻页无重复无遗漏。
3. 对比接口查询计数：1/10/50/200 候选查询数恒定；与旧实现逐字段等价（可读候选）。
4. 隐私：两种隐藏候选状态下主管的对比与 duplicates 响应除 case ID 外逐字节相同；总监完整。
5. 审核事务：50 候选时 POST 查询数不随 N 线性增长；自审、跨组、历史确认、版本冲突、并发两审核人同时裁决均保持原结果；审计字段不变。
6. 1k/10k 项目数据下 `EXPLAIN (ANALYZE, BUFFERS)` 记录，冷/热缓存分别给 P50/P95。
