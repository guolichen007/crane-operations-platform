# 27 G3-2A 跨组重复候选隐私收口验收

基线 `8caed9565e349f9bd7b6065a7b9768c5d83d789e`。该基线的八门 CI（Run 42171912765）在 `baobei-e2e` 失败：mobile-390 下 `g2-projects.spec.ts` 退出登录后立即访问 `/login`，会话尚未失效被重定向回首页，随后等待登录下拉框超时。先以独立提交 `ed9f239` 修复（四处退出后等待 `/login`，契约脚本增加守卫），再开始本批。本批只做跨组候选的最小披露，不进入 G3-2B / G3-2C。

## 1. 负责人裁决与实现口径

对当前账号无权读取的相关候选（`ProjectPolicy.Read == false`）：

- 允许：一条固定、粗粒度的“存在需上级核验的相关候选”提示，以及处理路径。
- 不允许：隐藏候选数量、风险等级、精确评分、匹配信号、客户、地区、设备、需求、创建时间、销售阶段、裁决状态、候选 ID、case ID、证据等级；也不允许为每个隐藏候选保留占位元素。
- 可读候选保持原有合法详情；服务端的权限、防自审、冻结证据和重复判断仍使用全部候选。

实现为统一的 Go 返回层投影（`services/project-intake-api/privacy.go`），不是前端 `v-if`：

| 字段 | 取值 | 依赖 |
| --- | --- | --- |
| `restrictedRelated` | 不存在隐藏候选时为 `null`；否则为固定对象 | 只依赖“是否存在 ≥1 个隐藏候选”与调用者角色 |
| `restrictedRelated.code` | `RESTRICTED_RELATED_PRESENT` | 固定 |
| `restrictedRelated.route` | 审核角色 `SALES_DIRECTOR`；销售 `REVIEWER` | 调用者角色 |
| `restrictedRelated.message` | 审核角色：“检测到需要跨组核验的相关项目。当前账号无权查看详情，请销售总监处理。”；销售：“检测到可能重复的已有报备。当前账号无权查看详情，提交后由审核人员核验。” | 调用者角色 |

销售看不到本组之外的项目，也无法区分隐藏候选来自哪个团队，所以销售文案不说“跨组”，只说提交后由审核人员核验。

## 2. 受影响接口

| 接口 | 修复前 | 修复后 |
| --- | --- | --- |
| `GET /projects/{id}/duplicate-comparison` | 隐藏候选占一个 case 槽位：`id`、`score`、`risk`、`signals`、`decision`、`restricted=true` | `cases` 只含可读候选；新增 `restrictedRelated`；`restricted` 字段只在服务端使用（`json:"-"`） |
| `GET /projects/{id}/duplicates` | 隐藏候选占一项：`score`、`risk`、`signals`、`region`、`createdAt`、`salesStage`、`message` | `items` 只含可读候选；新增 `restrictedRelated` |
| `POST /duplicate-checks`（销售/管理员实时查重） | 同上 | 同上；信息不足时返回 `restrictedRelated: null` |
| `GET /projects/{id}` 的 `review` | `pendingDuplicates` 计入隐藏候选 | 只计可读候选；隐藏候选只由 `relatedCandidates.reasonCode=REVIEW_RELATED_PROJECT_RESTRICTED` 表达 |
| `GET /reviews` 列表的 `review` | 同上 | 同上 |
| `POST duplicate-decisions` / `approve` | 不变：受限主管裁决 403 `REVIEW_RELATED_PROJECT_RESTRICTED`，批准被拒绝（403/409，测试按两者之一断言） | 不变（服务端仍按全部候选判定） |

另外两处让对照稳定的修复：候选查询增加 `ORDER BY registration_no, id`，对比查询增加 `created_at DESC, registration_no, id`，审计按 `created_at DESC, revision DESC, action, id` 排序。修复前同一毫秒内写入的记录顺序不确定，会在对照中产生与隐私无关的差异。

## 7. 契约与兼容性

OpenAPI 版本 `1.2.2-g32a`：新增 `RestrictedRelated`（可为 null）；`DuplicateComparison` 删除 `cases[].restricted`，新增必填 `restrictedRelated`；`/duplicates` 与 `/duplicate-checks` 的 200 响应新增必填 `restrictedRelated`；`ReviewEligibility.pendingDuplicates` / `legacyCandidates` 说明改为“仅可读候选”。

兼容性说明：

- 只新增字段、删除受限槽位，未改状态码、错误码与 404/403/409 语义，无数据库迁移。
- 依赖旧 `cases[].restricted=true` 槽位的客户端会看不到隐藏候选的占位；仓库内唯一客户端（项目报备 Web）已同批更新。
- 依赖 `pendingDuplicates` 判断“是否还需裁决”的客户端，对受限主管可能得到 0 而批准仍被拒绝。应以动作提示 `actions.approve` / `review.reasonCode` 为准（Web 已如此）。
- 对总监与管理员，响应内容与修复前相同（只增加 `restrictedRelated: null`）。

## 8. `duplicate-checks` 成员级限流 / 审计评估（仅分析，本批未加限制）

修复后，销售通过实时查重对隐藏候选只能得到一个布尔值：在给定客户/项目/省市组合下“是否存在至少一个我看不到的相关报备”。理论上可以反复改变输入来枚举这个布尔值。评估结论：

- 现状：接口要求登录会话与 CSRF，只对销售与管理员开放；单次查询为一次候选扫描。没有成员级计数。
- 不加硬阈值的理由：快速报备向导在输入客户、项目、省市、厂区、车间、招标号时会以 450ms 防抖自动查重，正常填写一份报备就可能触发十几次；多人同时录入或补录历史数据时更多。任何固定的每分钟上限都可能阻断合法报备，违反“不能临时加入会阻断合法报备的硬阈值”的要求。
- 建议（需负责人授权后在后续批次实施）：先做只记录、不阻断的观测——按成员、按小时累计查询次数与“返回提示”次数写入运维计数（不记录查询正文）；观测两到四周后，若出现明显异常，再按 P99 的倍数定软阈值（超限只降级为“提交后由服务端核验”提示，不拒绝提交）。生产安全与限流契约同步更新。
- 服务端提交时仍会重新查重并冻结证据，绕过前端查重不能逃避审核。
