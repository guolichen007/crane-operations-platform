# 58 · Baobei V1.1 生产初始化说明（7 人 1 团队）

**目标**：正式库只保留 OWNER（现有管理员）、1 名备用管理员、5 名销售和 1 个团队“销售一组”，不含任何旧业务数据；全部迁移、角色权限、不可变触发器、环境标记和身份纪元（Realm baobei）原样保留。

**工具**：`deploy/baobei/golive-init.py`。一次性使用，只由运维在部署宿主机运行。它没有网络或 HTTP 接口，只对 `u-dao-baobei` 的 `baobei-postgres` 容器执行（`docker exec` 本地 socket，以 bootstrap 角色连接）。

## 1. 原则

- **线上库不改不删**：工具不删除线上库的任何行，不禁用任何触发器，不使用 `session_replication_role`。它在旁边建一个干净库，校验通过后，在 API 停止期间用**一次重命名事务**切换。原库改名保留，并撤销所有应用角色的访问权，用于回退。
- **白名单**：表规则是白名单式的，每张表只有“全量保留 / 过滤保留 / 置空”三种之一。遇到工具未分类的表（例如以后新增迁移），工具直接停止，不会猜测。
- **审批与身份**：每个写步骤都要求 `--approval` 与白名单中的批准编号一致，并要求填写 `--operator`。
- **不改 Crane 和 Firebot**：不触碰 Crane、Firebot、共享入口和 Keycloak 的其他 Realm。

## 2. 表规则

| 规则 | 表 |
|---|---|
| 全量保留 | `baobei_migrations`、`identity_epoch`、`reference_values`、`baobei_environment`（如有） |
| 过滤保留（只留白名单人员） | `app_users`、`identity_links`、`staff_audit`、`profile_audit`；`teams` 重建为一个“销售一组” |
| 置空 | 项目、报备、审批、提交证据、参与、建项请求、位置、参与方、设备、需求、跟进、客户、联系人、客户审计、技术需求与修订/问答、重复案件、归属历史、交接、审计事件、会话、待登录、账号操作、出站队列、登记计数器等其余全部业务表 |

## 3. 白名单（私有 0600 文件，不提交仓库）

```json
{"approval": "OWNER-GOLIVE-20261119",
 "team": {"name": "销售一组"},
 "keep": [{"staff_id": "<OWNER 的 staff_id>", "role": "baobei_admin"}],
 "create": [
  {"name": "备用管理员", "role": "baobei_admin", "claim_login": "admin02"},
  {"name": "销售01", "role": "baobei_sales", "claim_login": "sales01"},
  {"name": "销售02", "role": "baobei_sales", "claim_login": "sales02"},
  {"name": "销售03", "role": "baobei_sales", "claim_login": "sales03"},
  {"name": "销售04", "role": "baobei_sales", "claim_login": "sales04"},
  {"name": "销售05", "role": "baobei_sales", "claim_login": "sales05"}]}
```

- **keep**：保留的现有成员，`staff_id`、`subject`、身份链接、手机号、角色、姓名都不变。成员必须是在用、可登录、有当前可信 Issuer 的身份链接、有正式手机号的管理员或总监。保留销售或主管会失去原团队，工具会拒绝，这类人请改为新建。
- **create**：新建成员，均为“待开通 + 待认领”，没有手机号，也没有 Keycloak 账号。销售自动归入“销售一组”。角色完全按 OWNER 的要求填写，不自行安排主管或总监。
- 上面的姓名只是占位，成员首次认领时会自己填写真实姓名。

## 4. 执行步骤（在 056acfd 之后的投产版本上线、CI 8/8 之后）

```bash
S=/srv/u-dao/ops/baobei-golive/state      # 0700，root 或运维账号本人
W=/srv/u-dao/secrets/baobei/golive-whitelist.json   # 0600
C=u-dao-baobei-baobei-postgres-1
# 工具只从“实际运行 SHA”的干净检出运行（git status 为空，HEAD = 运行 SHA）；
# 它与同目录的 direct-deploy.py 一起使用，不进入发布快照，因此不影响旧发布的工具核验。
G=/srv/u-dao/src/crane-operations-platform     # 已 checkout 到运行 SHA
T="python3 -I -B $G/deploy/baobei/golive-init.py --state-dir $S --whitelist $W --container $C"

$T inventory                                                  # ① 只读清单（DRY_RUN）：现有数据、保留人员（手机号遮蔽）、计划
docker compose ... stop baobei-api baobei-web                 # ② 停止应用（维护窗口）
$T --approval OWNER-GOLIVE-20261119 --operator <人> backup    # ③ 完整备份 + 隔离恢复校验
$T --approval ... --operator ... build                        # ④ 构建并校验干净库（线上不动）
$T --approval ... --operator ... swap                         # ⑤ 切换（一次事务）
$T --approval ... --operator ... verify                       # ⑥ 复核
direct-deploy.py up ...                                       # ⑦ 启动应用（同一投产版本）
```

**备份（第 ③ 步）**：

- 先确认 API 已停，备份前后表计数一致；否则拒绝，并提示先停 API。
- 用 `pg_dump -Fc` 备份，同时写出 sha256、迁移 ledger 和表计数清单（0600）。
- 把备份恢复到一次性库做核对，表计数和 ledger 都要一致，核对完删除该临时库。
- 备份文件放在状态目录下。迁到受保护持久目录前，**不得提交仓库**。

**构建（第 ④ 步）的校验项**，全部满足才判 PASS：

- 与线上库比对：结构指纹完全一致（列、约束、索引、触发器及其启用状态、函数定义与属主及 ACL、扩展、表与列授权），迁移 ledger 一致，身份纪元一致，数据库级权限仍是批准的最小集合。
- 业务表全部为空，团队只有 1 个，人员数等于白名单人数。
- 保留成员的身份字段逐项不变，待认领成员与白名单完全一致，至少有 1 名在用管理员。

**切换（第 ⑤ 步）**：

- 先确认 API 不在运行，线上库和干净库都没有任何连接。
- 重新核对备份未变，并重新校验干净库。
- 再先写入切换意图，然后执行 `ALTER DATABASE baobei RENAME TO baobei_pregolive_<时间>`、`ALTER DATABASE <干净库> RENAME TO baobei`，并撤销旧库的全部访问权。

## 5. 初始化之后（网页完成，不用后台代开通）

1. **OWNER 登录**：用现有手机号登录 → 人员管理里能看到 6 名“待开通 · 临时登录名”的成员。
2. **开通账号**：逐个点“开通登录账号”，页面只显示一次临时登录名和临时密码，线下当面或私信交给本人。
3. **成员首次登录**：用临时登录名和临时密码登录 → 设置新密码 → 填写真实姓名和本人手机号 → 用手机号重新登录。
4. **清理旧账号**：状态目录里的 `dropped-keycloak-users.json` 列出了不再进入正式库的旧成员的 Keycloak 用户 ID（只有 ID）。请在 Realm baobei 中停用或删除这些用户；否则它们的手机号用户名仍被占用，新成员认领该号会提示“已被使用”。
5. **统计确认**：数据分析、项目中心、跟进中心、客户中心都应为空，人员管理中有 7 人、1 个团队。

## 6. 回退

```bash
docker compose ... stop baobei-api baobei-web
$T --approval ... --operator ... rollback     # 干净库改名移开，原库改回 baobei 并恢复连接授权
direct-deploy.py up ...                        # 同一版本应用重新启动
```

- **原库不可用时**：用第 ③ 步的备份，按 60 号 §4 的数据库恢复流程处理。
- **旧库清理**：初始化旧库（`baobei_pregolive_*`）至少保留到最终验收和 Tag 完成之后；需要清理时由 OWNER 单独书面批准。

## 7. 隔离演练（已完成，桌面）

**演练环境**：一次性 PostgreSQL 18.4 集群，带生产角色（initialize.sql + staff-role.sql），装入全部 16 个迁移。数据是开发环境 E2E 产生的合成业务数据：36 个项目，以及审批、客户、联系人、跟进、技术需求、审计等；再加一名带正式手机号和身份链接的合成 OWNER，身份纪元设为 baobei。

**结果**：

- **全链路**：inventory → backup（恢复校验 PASS）→ build（结构一致、权限最小、业务表 0、7 人 1 团队）→ swap → verify → rollback（原库 36 个项目完整回来，生产迁移角色 `maintenance migrate` 校验通过）→ 再次 build/swap/verify，全部 PASS。
- **反例都被拒绝**：线上库有连接时切换、批准编号不符、未备份就构建、白名单无效（12 种）。
- **初始化后业务接口**：项目、跟进、客户都是空列表，数据分析总数为 0。
- **自动化**：`tests/baobei/direct/test_golive_init.py` 的 `IsolatedDrillTests` 在给出演练端口时会自动跑完整链路。
