## 1. CR-08A 维护窗口状态机

**问题：** 维护窗口只有一种阶段表，也就是数据库升级的 11 个阶段。同一 SHA 切换 Realm 时没有 SCHEMA_UPGRADE 可记，窗口只能停在中间，或者伪造升级阶段才能结束。

**修复：** 窗口增加 `kind` 字段，每种类型有自己的阶段表。

| kind | 阶段 |
|---|---|
| `upgrade`（默认；旧窗口文件没有 kind 时按此处理） | 与 G5-RC0 相同的 11 个阶段，不变 |
| `realm-switch`（路径 A，同提交另一 Realm，可双向） | MAINTENANCE_ENTER → **SWITCH_BASELINE_VERIFIED** → IDENTITY_PRECHECK → IDENTITY_SWITCH → NEW_API_START → WEB_START → SMOKE_TEST → RELEASE_COMPLETE |
| `disaster-recovery`（路径 B） | MAINTENANCE_ENTER → RECOVERY_BACKUP_VERIFIED → APP_STOPPED → DATABASE_RESTORED → RECOVERY_VERIFIED → OLD_API_START → WEB_START → SMOKE_TEST → RELEASE_COMPLETE |

**`switch-baseline` 命令**，机器实测后才记录：

- 当前没有 pending。
- active 是同一提交的另一 Realm。
- 两份清单都能核验通过，镜像与数据库契约完全相同。
- 线上 ledger 与该提交的迁移文件逐行一致；该行集合与清单中的数据库契约哈希绑定。
- 数据库权限是批准的最小集合（见 §2）。
- 数据库纪元仍指向当前 Realm。
- 目标 Realm 的专属密钥文件存在。

这一步不执行迁移，不写数据库，也不改动 PostgreSQL。

**`up`：**

- 同提交 Realm 切换必须在 realm-switch 窗口内执行。
- 启动后实测运行中的 API：镜像 ID、Issuer、Client、BAOBEI_IDENTITY_REALM，以及 Web 密钥挂载的来源文件。
- 经 Web 代理请求 `/auth/config`：API 必须报告已启用生产 OIDC 且没有开发登录，这说明 API 启动时对目标 Realm 的 OIDC discovery 已经成功。
- 这些都通过后，才记录 NEW_API_START / WEB_START，再更新 active。

**SMOKE_TEST / RELEASE_COMPLETE：** 新窗口（带 id）只有在 active 等于本发布且没有 pending 时才能记录，所以不能对一个尚未生效的发布宣布完成。

**中断与恢复：**

- 命令在启动后、写 active 前，或写 active 后、清除 pending 前中断时，重跑同一命令会继续执行：已记录的阶段不再重复，指针补齐。
- `abort-window --evidence …` 把窗口显式标为 ABORTED，记录停在哪一步以及当时的 active/pending。这个命令不改任何指针，也不会显示成功。
- 已结束（COMPLETE / ABORTED）的窗口归档到 `maintenance-history/`，不删除。
- `status` 给出窗口类型、下一步，以及“存在 pending”“窗口未完成”等提示。

**预检绑定：**

- 新预检记录中写入 `window_id`。旧窗口的预检记录（即使发布号、变更号相同，且在有效期内）不能用于新窗口。
- 原有绑定全部保留：Realm、Issuer、管理员、变更号、过期时间、工具哈希、封印。
- 专属 Realm 的 IDENTITY_PRECHECK / IDENTITY_SWITCH 仍只能由 preflight / switch 记录。SWITCH_BASELINE_VERIFIED 与各恢复步骤只能由工具记录，`phase` 命令拒绝手工记录这些阶段。

**旧格式兼容：**

- 旧窗口文件（没有 kind 或 id）按 upgrade 继续推进；已完成的旧窗口原样归档。
- G5-C-P0 白名单中的两个旧发布（7b95580、253b4a8）照旧核验。
- 本工具之前准备的发布清单没有 `web_secret` 字段，按当时挂载的 `oidc_client_secret` 核验。

## 2. CR-08B 路径 B 正式恢复入口

普通 `rollback` 遇到数据库契约不同仍然拒绝，行为不变。本轮还补上了一个旁路：回滚目标是同一提交的另一 Realm 时，`rollback` 也拒绝，必须走 realm-switch 窗口。

新增 `recover --step backup|stop|restore|verify|start`，在 disaster-recovery 窗口内按顺序执行，每一步都先实测前置条件。

| 步骤 | 工具做什么 | 拒绝条件 |
|---|---|---|
| backup | 确认失败发布（pending 或 active）清单中的 rollback_target 就是本目标，且两者数据库契约不同。核验备份文件的 sha256 与其 .json 清单一致；格式、数据库、环境为 production；清单中的迁移 ledger 与目标旧提交逐行一致。确认备份就是失败发布升级窗口 FRESH_BACKUP_VERIFIED 证据中记录的那一份（校验和），且创建时间在该窗口的 MAINTENANCE_ENTER 与 FRESH_BACKUP_VERIFIED 之间 | 校验和异常、相对路径、Schema 不是旧版、更早或另一份备份、找不到升级窗口 |
| stop | 只停止 API（不动 PostgreSQL），实测 API 已停止、业务连接为 0 | 仍有连接 |
| restore | 清理以前中断遗留的 `baobei_restore_*`。新建 `baobei_restore_<时间>_<随机>`，先收回 PUBLIC 权限并只授予四个业务角色 CONNECT。`pg_restore --no-owner` 之后把 public 下的对象属主统一改为 baobei_migrator（与迁移器创建时一致）。在临时库上实测 ledger、权限、身份状态和表计数，全部一致后，在一个事务内把现库改名为 `baobei_failed_<…>`（收回全部业务访问权），把临时库改名为 `baobei`。改名前先把“将要交换”写入窗口，重试时只有确认是本工具自己完成的交换，才跳过重复恢复 | 任一核验失败时：删除临时库，现库原样不动，阶段不前进 |
| verify | 在 `baobei` 上再次实测 ledger、最小权限、身份状态（旧版本不得有 identity_epoch）和表计数 | 有人重新迁移、权限被放宽 |
| start | 写入 pending（失败发布），只启动 Web/API，核对运行镜像 ID，核对运行容器的 Realm、Issuer、Client 和 Web 密钥来源（旧版仍为 `oidc_client_secret`），检查 `/auth/config`，再次核对数据库，然后才更新 active=目标并清除 pending | 不健康、镜像不符、认证未配置、密钥来源不符：指针不动，pending 保留，status 提示 |

**最小权限集合**，来源是 initialize.sql + staff-role.sql：

- 四个业务角色都能登录，不是超级用户，没有 CREATEDB / CREATEROLE / REPLICATION / BYPASSRLS，不属于任何其他角色。
- 对 baobei 只有 CONNECT，没有 CREATE / TEMP，不能连接任何其他数据库。
- public schema 只有 USAGE；只有 baobei_migrator 有 CREATE。
- PUBLIC 对数据库、schema 和表都没有权限。
- 除扩展对象外，public 下所有对象的属主都是 baobei_migrator。

**真实 PostgreSQL 18.4 演练：**

- 准备：按生产方式初始化（initialize.sql + staff-role.sql，以 baobei_migrator 执行旧版 00001–00004 与授权），写入数据，`pg_dump -Fc --no-owner` 备份。
- 用工具自己的 SQL 检查初始化结果：最小权限 PASS。
- 逐项放宽后都被拒绝：TEMP、连接 postgres、public CREATE、表授予 PUBLIC、角色成员关系、数据库授予 PUBLIC、表属主改为 bootstrap。
- 按 restore 步骤执行：刚 `pg_restore` 完时被拒（属主是 bootstrap，即服务器上实际遇到的权限问题）；属主修正后 PASS。ledger 与表计数一致，交换后现库仍是最小权限。
- 恢复前后，权限与属主指纹完全一致。
- baobei_runtime 能读恢复后的库，不能连接被保留的失败库。
- 遗留临时库可以识别并删除。
- 演练中发现并修复了一个真实缺陷：最初用一条 CASE + to_regclass 语句判断旧 Schema 的 identity_epoch，在旧 Schema 上会在解析阶段报错。已改为先判断表是否存在，再单独查询。

**运行手册（替代 45 号文档 §6 路径 B 的人工步骤）：**

1. `abort-window` 结束失败的升级窗口。
2. `phase --phase MAINTENANCE_ENTER --window-kind disaster-recovery --source-sha <旧 SHA> --identity-realm crane`。
3. 按顺序执行 `recover --step backup --backup <升级前备份>`、`recover --step stop`、`recover --step restore`、`recover --step verify`、`recover --step start`。
4. 冒烟测试通过后，记录 SMOKE_TEST 和 RELEASE_COMPLETE。

全程不需要手工编辑 active.json。备份之后的业务写入（RPO）仍按 45 号文档 §6 逐条导出处置；失败库以 `baobei_failed_<…>` 保留，供核对。

## 3. CR-08C 独立 Realm 密钥隔离

| Realm | 外部密钥文件 | 容器内路径 |
|---|---|---|
| crane（现网、旧发布、路径 B） | `oidc_client_secret`（名称不变） | `/run/secrets/oidc_client_secret` |
| baobei | `baobei_oidc_client_secret` + `account_client_secret` | 同上 |

- 两个 Realm 各用自己的密钥文件，路径 A 双向切换都不需要人工替换或覆盖密钥。
- baobei 缺少专属文件时 fail-closed，不会回退到 crane 的文件。专属文件内容与 crane 相同时也拒绝，因为这正是“复制或覆盖同一文件”的情况。
- `check_identity` 核验渲染后 `secrets.oidc_client_secret.file` 是本 Realm 的文件名，并且没有明文 `OIDC_CLIENT_SECRET`。生产门禁（production-gate.mjs）也加了同样的约束和反例。
- 新清单记录 `web_secret` 的文件名，不记录值。
- 环境变量不能改变 Realm 或密钥：工具不读取这些变量，Docker 调用前会丢弃 BAOBEI_* 和 COMPOSE_* 变量。
- 预检必须使用密钥目录中本 Realm 的文件（`--web-secret-file` 指向别处时，在调用 Keycloak 之前就拒绝）。工具在真实登录前后都计算该文件的 HMAC 指纹（密钥是状态目录私有的封印密钥），两次必须一致，然后写入预检记录。之后执行 `up` 时重新计算，与预检时不同就拒绝。
- 密钥值不写入日志、Git、清单、窗口或证据：测试断言 preflight.json 与窗口中都不含密钥原文。

### 8.1 先走路径 A、再走路径 B：发现缺陷并修复

**复现：** 使用真实的 prepare、apply、realm_switch 和 recover。
1. 升级窗口属于 `<SHA>+baobei`。
2. 升级完成后走路径 A 回切 crane，此时 active 为 `<SHA>`。
3. 在 disaster-recovery 窗口内执行 `recover --step backup`。

ebd96aa 在这一步报“找不到失败发布的升级维护窗口记录”。原因是 `upgrade_window_of` 按完整的发布标识匹配，而升级窗口记在另一 Realm 的发布标识下。结果正式的升级前备份无法使用，路径 B 被堵死。这是 fail-closed，没有安全旁路，但恢复入口无法完成。

**修复（最小）：** 新增 `upgrade_releases`。失败发布本身之外，只追加同一提交另一 Realm 的发布，且必须同时满足：
- 该发布的清单能通过核验；
- 它的 rollback_target 与失败发布的 rollback_target 都等于本次恢复目标；
- 两者的数据库契约相同；
- 两者的镜像相同。

只有满足这些条件，它的升级窗口才算作同一次升级。原有约束全部保留，没有任何一项被取消：
- 备份校验和必须等于 FRESH_BACKUP_VERIFIED 证据中记录的值；
- 备份必须在 MAINTENANCE_ENTER 与 FRESH_BACKUP_VERIFIED 之间创建；
- 备份清单中的旧 ledger 必须与目标旧提交一致；
- 失败发布的 rollback_target 必须等于恢复目标，且数据库契约必须不同。

工具不会因为“Schema 相同”就随意挑一份备份。阶段记录中会写入 `upgrade_releases` 与 `upgrade_window`，供审计。

### 8.2 旧版 backup.mjs 兼容（真实 PostgreSQL 18.4）
