## 1. E2E 数据污染根因收口

### 1.1 根因与确定性反证

共享 e2e 库的审核队列按“冻结提交时间”升序排列，每页 20 条。旧写法把清理放在用例的最后一行（A0-7、g33a 用过 `finally`，但清理的是“提交之后”才知道的 ID；g34a0-dashboard 把清理写成最后一个独立用例）。只要用例在“提交成功之后、清理之前”失败，这条报备就留在队列前部。`staff.spec` 默认目标在第 1 页，于是出现与本用例无关的连锁失败。

反证脚本 `repro/pollution.spec.ts` 用旧写法跑 20 次“提交后立即失败”的用例：

### 1.2 修复：测试基础设施，不改业务规则

新增 `tests/baobei/e2e/support/isolation.ts` 与 `support/global-setup.ts`。

| 要求 | 做法 |
| --- | --- |
| 唯一运行标识 | `RUN` 由 global-setup 生成，所有 worker 共享；`uniq(prefix)` = 前缀-RUN-pid+序号。g34a0-dashboard 的示例数据改为 `A0示例<RUN>`，不会误用上轮残留（原来按“已存在就跳过”判断，上轮残留的日期还会过期） |
| 统一清理 | `cleanup` fixture：提交**之前** `cleanup.track(id)`，用例结束（通过或失败）后由总监退回，总监不独立时回退到管理员。g34a0-dashboard 的清理改为 `afterAll` |
| 清理失败不静默 | 无法退回时 fixture 失败并列出项目 ID、编号、当前状态和原因，例如 `GET 404 NOT_FOUND`、`return 409 …` |
| 不默认第 1 页 | `staff.spec` 改用 `findCard` 逐页定位（与 g32b 同一过程），找不到时报出视图、页码与目标 |
| 强杀后 | 普通失败由 fixture 在 finally 中清理；进程被强杀时不会执行任何清理。global-setup 在用例开始前**只列出**已有待审报备（ID、编号、状态、名称），**不修改**——它们可能属于其他运行或人工检查。默认继续运行（运行标识 + 翻页定位使残留无法导致失败）；`BAOBEI_E2E_REQUIRE_CLEAN=1` 时直接失败并要求重建库（CI 每个 job 都是全新 PostgreSQL service 容器；本地删除并重建回环测试库）。只在 development + dev 登录的合成栈上执行 |
| 不弱化断言 | 旧断言一条未删；没有延长超时，没有新增固定等待 |

涉及文件：`staff.spec`、`g34a0-cross-step`、`g34a0-dashboard`、`g33a-pipeline`、`g33b-statistics`、`playwright.config.ts`。
