## 3. 四角色业务 UAT

### 3.1 形式

可执行脚本 `tests/baobei/uat/uat.spec.ts`（`uat.config.ts`，不进 CI）。共 34 个步骤，每步都记录测试身份、操作、页面截图、对应 API 与服务端状态，以及 PASS/FAIL；前序失败导致未执行的步骤由 `uat-report.mjs` 标为 BLOCKED。非开发人员可以照下表手工执行，或运行：

```
node node_modules/@playwright/test/cli.js test --config ../../tests/baobei/uat/uat.config.ts   # 在 apps/project-intake-web 下，合成栈已启动
node tests/baobei/uat/uat-report.mjs                                                             # 生成结果表
```

**数据。** 只用 dev 登录合成身份（synthetic-a/b/c、manager、manager-other、director、admin）。项目名带 `UAT-<运行标识>`，没有导入任何真实客户资料。运行结束后，UAT 提交的报备由清理逻辑退回。

**前置条件。** 合成栈（`APP_ENV=development`、`DEV_AUTH=1`）、PG 18.4，可以是空库或已有数据的库（第二次运行在已有数据的库上同样 34/34）。

## 5. 性能与数据一致性

**同机 A/B 设置。** `b8b1606` 与 `886f75c` 的 API 和测试二进制由同一 Go 1.27.3 分别从 git 构建。两者在同一 PG 18.4 实例（生产 digest 解包）、同一份 10k 合成快照上交替轮次测量（BAAB…），每轮新建连接池，并冷重启 PG 测首请求。

**环境。** i7-13700KF 共享虚拟机 2 vCPU、3.9 GiB 内存，测量期间 loadavg 0.86–1.43（`perf/machine.txt`）。本批没有新增 SQL、缓存、物化视图或迁移。

**服务端，单客户端顺序请求，每轮热 5 次，每角色 3 轮。** 各轮 P50 的中位数见下表（原始数据 `perf/server-prog.txt`；SQL 计划与 pg_stat_statements 见 `perf/sql-report-*.md`）：

| 角色 | 首页两请求合计 b8b1606 P50/P95 | 886f75c P50/P95 | ΔP50 | 查询数 | JIT |
| --- | --- | --- | --- | --- | --- |
| 销售 | 29.9 / 33.1 ms | 28.9 / 31.3 ms | −3.3% | 9 / 9 | 0 |
| 主管 | 66.5 / 72.7 | 66.5 / 74.8 | 0.0% | 9 / 9 | 0 |
| 总监 | 135.4 / 140.4 | 136.5 / 146.9 | +0.8% | 9 / 9 | 0 |
| 管理员 | 85.2 / 88.2 | 85.9 / 90.7 | +0.9% | 9 / 9 | 0 |

单接口差值都在 ±5% 以内，只有销售 workspace-summary 为 −12.7%（3–4 ms 量级，属轮次波动）。两版 SQL 与执行计划相同。33 号文档记录的“主管 41.5 ms 对比 30 号 28 ms”在同机交替测量下不再出现：两版都约 40 ms。那次差异来自不同时间、不同轮次的沙箱环境，不是代码退化。

**浏览器首屏，真实页面，每角色 20 次。** 测量从导航开始，分别记录：首张任务卡可点击的时刻，两个请求的起止与重叠，以及阶段面板可见的时刻（`perf/browser-summary.md`）：

| 角色 | 任务卡可操作 P50/P95：b8b1606 → 886f75c | 两请求重叠 P50 | 阶段面板可见 P50/P95（仅 886f75c） |
| --- | --- | --- | --- |
| 销售 | 47/67 → 57/77 ms | 14 ms | 62/80 ms |
| 主管 | 74/132 → 82/104 | 37 | 86/107 |
| 总监 | 119/127 → 94/150 | 50 | 97/153 |
| 管理员 | 122/131 → 97/150 | 45 | 100/153 |

两个请求确实并发，重叠时间约等于较短请求的耗时。886f75c 的首页比 b8b1606 多一个并发请求和一块面板。在 2 vCPU 上，销售首屏中位数慢约 10 ms，总监/管理员中位数反而快约 25 ms，P95 有 +20 ms 左右的尾部。

**结论。** PERFORMANCE_AB_COMPARISON=PASS：服务端没有可确认的退化，所有角色首屏可操作时间都在 160 ms 以内。

**登记 P3-PERF-1（观察项，未确认为退化）。** 销售首屏 +10 ms、总监/管理员 P95 +20 ms，可能来自两个请求在 2 vCPU 上的争用。需在 CI 规格机器上复测后才能判断；按要求，本批不做缓存或 SQL 优化。
