## 2. 修复

**direct-deploy.py**

- `prepare --identity-realm crane|baobei`，默认值为 `crane`，与现状完全相同。
- Realm 写入不可变清单：`identity_realm`、`identity_issuer`，并与 `source_sha`、`snapshot_sha256`（快照现在包含 `compose.realm-baobei.yaml`）、`compose_sha256`（按 Realm 渲染）、镜像 ID 和 `database_contract_sha256` 绑定。
- 发布标识规则：crane 发布沿用原有 SHA，因此现有状态目录不受影响。baobei 发布为 `<SHA>+baobei`。同一提交的两个 Realm 复用已核验的同一组镜像。
- 之后的 `db/migrate/up/rollback` 只从已核验的清单读取 Realm，没有任何环境变量入口。
- `check_identity()` 校验渲染后的 Compose 必须与批准的 Realm 完全一致：
  - Realm、Issuer、Client 必须是批准值。
  - baobei 必须有 `BAOBEI_ACCOUNT_CLIENT_ID=baobei-account-service`、`/run/secrets/account_client_secret`，且密钥文件来自外部密钥目录。
  - crane 不得出现账号服务。
  - 任何一项不一致都会失败，不会继续部署。
- `check_mounts` 按 Realm 要求密钥文件，baobei 缺少 `account_client_secret` 时在调用 Docker 之前就拒绝。
- 改变 Realm 的 `up`/`rollback` 必须带 `--confirm-realm <目标>`，并且必须在 identity-switch 完成之后。
- **升级顺序门禁**：候选版本与当前版本的 `database_contract_sha256` 不同（不兼容迁移）时：
  - `migrate` 要求 `SCHEMA_UPGRADE` 恰好是下一阶段，`up` 要求 `NEW_API_START` 恰好是下一阶段。
  - 阶段由 `phase --phase X --evidence <编号>` 顺序记录，或由工具在 migrate/up 成功后自动记录（SCHEMA_UPGRADE、NEW_API_START、WEB_START）。
  - 阶段记录不能跳过、不能重复，不同发布之间互不通用；`status` 用于读取当前状态。
  - 工具不会自行停机、备份或切换 Realm。
- 原有保护保持不变：本地镜像校验、运行容器镜像 ID 校验、仅 `--no-deps` 启动 Web/API（PostgreSQL 不随升级重建）、数据库契约不同则拒绝旧镜像回滚、T5 变异检查。

**identity-switch（Go）**

- `precheckSwitch` 在 RR 只读快照中执行，任何异常都按失败处理，不会当作通过：
  - Schema 清单或校验和不符、表缺失、查询失败：`errSwitchSchema`。
  - 没有身份纪元且目标是独立 Realm：`errSwitchEpoch`。只允许在共享 Realm 首次建立纪元。
  - 必须指定 `--takeover-admin <staff_id>`，且该成员必须同时满足：角色为 `baobei_admin`，状态 ACTIVE，账号不处于 CREATING/REVIEW，有大陆工作手机，并且能在目标 Realm 登录（独立 Realm 要求存在 identity_links；共享 Realm 要求 subject 为 UUID 且不是在独立 Realm 新开户的成员）。
- dry-run 与正式切换使用同一个预检；正式切换另外要求 `--approval <接管方案编号>`，并在切换事务内、身份锁之下重做预检，任何变化都中止切换。
- 报告中包含 `sessionsToRevoke`、`linkedAdmins`、`cannotSignIn`（切换后无法登录的人数）。工具不会报告“全员切换成功”。

**identity-migration.py links**

- 写入 SQL 前，逐行在实时库里复核 staff_id、subject、role、staff_status、work_phone，并检查该 issuer 下是否已有链接。名单过期时整个事务中止。
- 因为 SQL 中含有已批准的手机号，改为写入新的 0600 私有文件（`--out`），终端只输出脱敏摘要。

**测试凭据**

- 真实 Keycloak 浏览器夹具改用私有交接文件 `BAOBEI_KC_CREDENTIAL_FILE`：只能放在 0700 目录中，以 O_EXCL、0600 新建，读取一次后立即删除，退出时也会清理。
- stdout 只输出夹具 URL。
- 新增静态门禁（CI contract 门执行），禁止测试代码打印 TemporaryPassword、手机号凭据、token 或 secret。

## 5. 回退与恢复

**路径 A：保留新 Schema 和新镜像，只切回共享 Realm**

- 适用于身份问题，且数据库契约相同的情况。
- 步骤：
  - 进入维护。
  - `identity-switch --realm crane --takeover-admin <能在 crane 登录的管理员> --approval …`，会吊销所有会话。
  - `up --identity-realm crane --confirm-realm crane`，使用同一 SHA 的 crane 发布。
- 已知限制：在独立 Realm 新开户的成员没有共享 Realm 账号，切回后无法登录，会计入 `cannotSignIn`，需要人工处置。工具不会报告全员回退成功。
- 业务数据无损。

**路径 B：恢复升级前备份并使用旧镜像**

- 适用于迁移失败或新版本数据错误。
- `direct-deploy rollback` 遇到数据库契约不同会拒绝，必须走经审查的恢复流程：
  - 进入维护并停止写入。
  - **先导出备份之后的所有写入**：按时间导出审批、审计、跟进、项目的新增和修改，交业务负责人逐条处置。不得静默丢弃。
  - 在隔离库执行 `restore-test` 验证备份。
  - 停止 API，替换数据库（恢复备份）。
  - 部署旧 SHA 的 crane 发布，冒烟测试通过后解除维护。
- **RPO** = 从备份时刻到停止写入之间的业务写入。维护窗口内写入已冻结，所以正常情况下 RPO 为 0；如果在恢复前解除过维护，则以导出清单为准。
- 不得把备份后产生的数据直接覆盖丢弃。
