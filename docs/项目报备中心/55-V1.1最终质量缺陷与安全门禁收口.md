### 门禁实现

| 文件 | 作用 |
|---|---|
| `tests/baobei/security/audit-gate.mjs` | 运行 `npm audit --json`（全量）和 `npm audit --omit=dev --json`（只看生产依赖），再运行 `npm view picomatch time --json`（检查是否已有官方修复），把原始 JSON 保存到 `local-private/baobei/security-audit/`。CI 用 `if: always()` 上传为 artifact，保留 90 天 |
| `tests/baobei/security/audit-gate-core.mjs` | 判定逻辑，见下 |

`audit-gate-core.mjs` 的规则：

- 审计等级仍为 high，没有降低，也没有其他任何忽略项。
- 只有以下条件全部满足才 PASS：
  - 全量报告中的每个 high 项要么就是 picomatch 本身，且它只带这一个获批公告（url、source、range、severity 全部一致）；要么是在 `via` 链上**只能追溯到 picomatch**、并且列在批准清单里的传播包。
  - 报告里出现的每个节点都在 package-lock 中，并且是 dev。
  - lock 中的 picomatch 节点与批准清单完全一致，包括版本和完整性值。
  - 生产依赖报告里没有任何 high 或 critical。
  - 报告的 metadata 计数与条目一致。
- 输出 `BAOBEI_NPM_AUDIT=PASS_WITH_APPROVED_EXCEPTION`，并列出未修复漏洞、受影响节点和截止日。
- 如果报告中已经没有任何 high，输出 `PASS`，并提示移除 SEC-EX-001。

`tests/baobei/task.mjs` 的 security 步骤从 `npm audit --audit-level=high` 改为运行上面这个门禁及其负例测试；govulncheck 和 gitleaks 照常执行。

## 2. AC-13 深滚动丢失（UAT 问题，已复现、修复）

**复现过程**：

- 无网络延迟时，300、835、1200 px 都正常。
- 给接口加 800 ms 延迟后复现：在桌面端翻到第 2 页，新一页还没加载完时滚到 835 px 并打开预览，数据返回后页面跳到约 0–48 px。
- 加入滚动与 DOM 变更追踪后确定根因：列表数据返回时会整体替换 20 行（keyed 行全部移除再插入），同时“正在加载报备…”这一行被移除、页面高度变化，浏览器的滚动锚点失效，滚动位置被钳到顶部附近。
- 300 px 时页面高度余量足够，所以看起来“正常”；服务器网络比本地慢，所以在服务器上出现。

**修复**（`Projects.vue` 与 `style.css`）：

- 列表数据替换前记录 `scrollY`，`nextTick` 后如果发生偏移就恢复原位置。
- 列表已经有数据时，刷新提示改为浮动显示（`.list-refreshing`，固定定位），不再占用一行。
- 其余逻辑都没有改：预览面板、背景滚动锁（reka-ui）、焦点恢复（Modal.vue 的 `returnFocus`）、进入详情时的路由滚动记录（`scroll-memory.ts`）。

**浏览器测试** `v11-final-ac13-deep.spec.ts`（desktop 与 mobile-390）：

- 40 个项目翻到第 2 页，滚到 835 px（桌面端第 2 页较短时滚到底），在接口延迟 0 ms 和 800 ms 两种条件下各跑一遍。
- 覆盖的操作：打开预览后用按钮关闭、用 Esc 关闭；从预览进入详情后用应用内返回按钮返回、用浏览器后退返回；关闭预览后焦点回到原项目。
- 除了位置误差（预览前后 <5 px，返回后 <60 px），还断言**原项目仍在可视区内**，并且按项目名精确匹配，避免把 “-3” 匹配成 “-30”。
- 另外加了一项“深滚动时列表整体刷新（慢网络）”：把第 2 页的请求挂起，在此期间深滚动并打开预览，再放行请求。修复前位置偏移 41 px，desktop 和 mobile 都 FAIL；修复后都 PASS。

## 3. 审批历史保护：迁移 00015

**先确认没有正式流程需要改写审批记录**：

- 代码中对 approvals 只有 governance.go 决策事务里的一处 `INSERT`。
- 通过、退回、重提、复审、驳回、结案、移交都只追加新行。
- 没有外键级联写入 approvals；identity 与 staff 维护命令都不触碰它。
- 运行角色原本就只有 `SELECT` 和 `INSERT` 权限。

**迁移内容** `00015_approval_immutable.sql`：

- `BEFORE UPDATE OR DELETE … FOR EACH ROW` 与 `BEFORE TRUNCATE … FOR EACH STATEMENT` 两个触发器，复用 `project_evidence_immutable()`，报错码 BB002。
- 00001–00014 字节未改。
- 这些触发器**不能**阻止一个能禁用触发器的超级用户。

**测试**：

- `TestDatabaseV11FinalApprovalImmutable`（真实 PG 18.4）：
  - 依次走真实的通过、退回→重提→复审通过、驳回、通过后移交，共 4 条审批记录。
  - 7 种普通误操作全部报 BB002，审批记录指纹不变：改理由、改决定、改审批人、按项目删除、全部删除、`TRUNCATE`、`TRUNCATE … CASCADE`。
  - 之后正常业务仍能追加审批。
  - 两个触发器都处于启用状态。
- `TestDatabaseProductionPrivileges`（生产角色夹具）：
  - runtime、maintenance、staff_api 执行 UPDATE、DELETE、TRUNCATE 都报 42501（无权限）。
  - 表属主 baobei_migrator 执行时被触发器拒绝，报 BB002。
- **变异验证**：去掉 00015 后，以上两个测试都 FAIL。
