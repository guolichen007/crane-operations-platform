## 2. A：登录、退出与重新认证

- **退出登录**（`auth.logout` / `auth.logout-confirm`）：服务端删除本会话、清 Cookie；旧 Cookie 调业务接口 401；重复退出幂等返回 `alreadySignedOut`；同浏览器其他标签页经 BroadcastChannel 同步退出。只结束 Baobei 会话，不影响 Crane 等其他应用。
- **切换账号**（`auth.switch`、登录页 `auth.login-switch`）：先退出，再 `GET /auth/login?account=switch` → Keycloak `prompt=login`，必须重新输入账号。普通登录不加 `prompt`，保留 SSO 便利。
- **退出企业账号**（`auth.logout-sso`）：`POST /auth/logout?scope=sso` 返回 discovery `end_session_endpoint` + `client_id` + `post_logout_redirect_uri`（Keycloak 26 RP-initiated logout，不用已废弃的 `redirect_uri`）；对话框写明会退出所有应用。
- **重新认证只用于敏感操作**：邀请主管/总监/管理员、角色变更、身份核验、高级账号恢复、修改高级成员邮箱、调整主管团队。普通资料（姓名、电话、备注）和销售业务权限调整不再要求密码。服务端判定，前端只做提示。
- **续办**：敏感操作在弹窗内显示“验证企业账号并继续”，保存当前表单（sessionStorage，5 分钟，同标签页，绑定操作者与成员版本）→ `prompt=login&max_age=0` → 返回原成员与原操作（`?resume=`），恢复表单并显示剩余有效分钟；服务端用签名 `auth_time` 与 nonce 判断，超时提示重新验证并保留输入；伪造或延长草稿时间被丢弃，未来时间的 auth_time 不被接受。

## 3. B：成员从创建到可登录

列表显示状态与下一步：待开通（请审核开通）→ 开通中（等待身份运维创建企业账号并登记）→ 待首次登录 → 已启用；开通失败显示原因与“重试开通”；已停用可恢复或归档。详情有四步进度条和操作历史。

**身份开通架构结论**：常驻 API 不持有 Keycloak 管理权限。13 号文档的 FGAP V2 夹具只证明临时 Realm 可配置单用户/四角色范围，未证明生产共享 Realm 的继承关系，因此**不授予常驻 API manage-users**，不宣称已实现自助开户。新增 `POST /api/v1/staff/{id}/provision-review`：管理员审核并生成开通回执草稿（含唯一 Client Role、手机、可选的 Keycloak 用户 ID），只记录审计 `staff.provision.review`，不绑定身份；绑定仍由 root-only 回执文件经 `maintenance staff-provision` 执行（dry-run、同字节重放幂等、版本/邮箱/手机不符拒绝、同一 subject 不能绑定两人）。真正的受控身份服务仍需另行建设。

## 4. C：工作手机必填、邮箱选填与表单

- 迁移 00005：`work_phone` E.164，CHECK 约束（国内只接受 `+861[3-9]` 11 位）、部分唯一索引；`baobei_staff_api` 增加该列 INSERT/UPDATE，`baobei_runtime` 不可读。
- 服务端：新建必填手机；历史成员可暂空、不可清空；国内 11 位、86/0086/+86 前缀规范化；重复手机/邮箱分别报 `STAFF_PHONE_DUPLICATE`/`STAFF_EMAIL_DUPLICATE`；姓名不能只含数字；字段级错误码。列表手机脱敏，详情完整显示，范围外主管看不到。
- 无邮箱开通：回执须写明唯一且等于记录角色的 Client Role、`uniqueEmail=false`；激活时须精确 subject + 单一匹配角色，多角色或错角色拒绝。有邮箱的成员仍校验已验证邮箱一致。
- 表单：姓名*、工作手机*、角色*、团队*（销售/主管）、邮箱（选填）、备注（选填）；普通新增和资料编辑记录默认原因，角色/团队/停用/移交等必须写原因；错误摘要 + 就近提示 + 聚焦首个错误；请求失败保留输入。项目表单的草稿/提交/审核分层规则沿用 G1–G3 已冻结契约，本批未改动。
