## 1. CI Run 44027107200 Attempt 1 的真实结果与原因

| Job | 结论 |
|---|---|
| contract / security / web-quality / build / api-test | success |
| baobei-db-test | **failure**（`node tools/task.mjs baobei race` 步骤，约 6 分钟后失败） |
| baobei-e2e | skipped（依赖 db-test） |
| baobei-compose | **failure**（`restore-test` 步骤，1 秒内失败；其余步骤 success） |

GitHub 作业日志需要仓库管理员权限（API 返回 403），所以本地按 CI 的方式逐项复现：`go test -race ./...` 跑在真实 PostgreSQL 18.4 上，并把以往在本地跳过的、依赖 Docker 的 `TestDatabaseG1BackupAndOldSchemaGate` 也跑起来（用 shell shim 把 `docker exec` 转发给本机 PG 18.4 客户端工具）。

结果有两项：

1. `TestDatabaseG33P0Equivalence` 在 R4 之后会真实失败：首页汇总新增了 `followup*` 计数，而这个等价性预言机还要求字段集合与旧实现逐字节相同。本地之前没发现，是因为它和 JIT 范围测试共用 `g33Data`，在无 JIT 的服务器上会被整体 Skip（CI 的 postgres:18.4-alpine 带 LLVM，所以会运行）。**这是 db-test 失败的原因。**
   修复分两点：JIT 跳过条件只作用于 `TestDatabaseG33P0JITScope`，等价性测试在任何服务器上都运行；等价性比较时，除新增的 `followup*`（由 V11 跟进中心测试证明）外，其余所有旧字段仍要求逐字节相同，出现其他新字段一律失败。
2. Go 侧的备份恢复测试和旧 schema 门禁测试本地实测 PASS。
3. **compose 失败的原因**：`tests/baobei/backup.mjs` 维护了一份精确的产品表白名单，库里出现白名单外的表就拒绝备份（“Refuse mixed-product/unknown tables”），而 V1.1 的 00009–00012 新表没有加进去。本地用 `BAOBEI_DB_TOOL=local` 对迁移到 00013 的库复现：30ab9d9 版工具拒绝，修复后 `BACKUP=PASS`、`RESTORE_TEST=PASS`（41 张表计数、迁移清单和关键关系都校验通过）。修复方式：把 8 张新表补进白名单，并新增 `TestDatabaseV11R7BackupTableList`，让白名单与实际迁移出的 schema 双向一致（去掉修复后该测试会失败），以后的迁移不会再悄悄破坏恢复测试。

**未做的事：** 没有以重跑 CI 代替修复。
