# Baobei 直接部署与回滚

直接部署是首次部署的默认路径。Linux 部署主机从经审查的 Git 提交构建两张本地镜像。Docker 构建需要访问 Dockerfile 的公共基础镜像和锁定依赖来源。首次启动 PostgreSQL 可能需要获取生产 Compose 已固定 digest 的镜像。GHCR 发布仍可按原独立流程执行。

## 部署前准备

使用独立产品工作树和本机 Docker Engine。安装 Git、Python 3.9+、Docker BuildKit 及支持 JSON 配置渲染的 Docker Compose。每台部署主机使用一套权限为 0700 的状态目录，归部署操作者所有。密钥目录位于工作树和状态目录之外。将四个运行凭据和单独的迁移 DSN 放入受控目录，文件权限遵循生产部署契约。

保留专用 PostgreSQL 数据卷和 `u-dao-baobei-frontend` 外部网络。共享 Ingress 继续转发 HTTP-01 至 Baobei Web。运维预先创建 `/srv/u-dao/platform/ingress/acme-webroot` 并检查权限。Web 只读挂载该目录。三个服务无宿主端口，Web 与 API 在容器内分别使用 8080 和 8088。

获取官方产品分支，再检出经核准的完整 SHA。变量由部署负责人指定。

~~~bash
git fetch --no-tags origin refs/heads/product/baobei-v1:refs/remotes/origin/product/baobei-v1
git switch --detach "$SOURCE_SHA"
git status --porcelain
~~~

`prepare` 核验 HEAD、干净工作区、官方 origin 和产品分支远端跟踪引用的祖先关系。核准的历史提交也可直接部署。

## 构建、迁移与启动

~~~bash
baobei_direct() {
  local command="$1"
  shift
  python3 deploy/baobei/direct-deploy.py "$command" \
    --source-sha "$SOURCE_SHA" --state-dir "$BAOBEI_STATE_DIR" \
    --secrets-dir "$BAOBEI_SECRETS_DIR" "$@"
}

baobei_direct prepare
baobei_direct db
# 首次初始化后，按生产部署契约设置独立角色密码和 DSN。
baobei_direct migrate --migrator-dsn "$BAOBEI_SECRETS_DIR/migrator_database_url"
# 首次开户时，按生产部署契约使用独立维护身份执行获批清单。
baobei_direct up
~~~

- `prepare` 从 Git 对象提取白名单文件。Docker 构建上下文只包含 Web、API 构建输入和单文件 Nginx 配置。运行凭据由部署阶段以文件挂载。
- Go 模块默认使用 `https://proxy.golang.org,direct`。网络无法访问时，部署负责人可显式设置 `BAOBEI_GOPROXY=https://goproxy.cn,direct`。清单记录所用地址，依赖仍按仓库的 `go.sum` 校验。
- 镜像采用 `baobei-local/baobei-web:<SOURCE_SHA>` 和 `baobei-local/baobei-api:<SOURCE_SHA>`。构建入口校验镜像可运行性、构建返回的 ID、OCI revision、官方 OCI source 和本机 Linux 架构。
- `releases/<SOURCE_SHA>/manifest.json` 记录源 SHA、平台、构建时间、本机引擎的两个镜像 ID、Compose 与部署文件哈希、数据库契约哈希和上次生效版本。保留快照和对应镜像以供审核及回滚。
- `db` 仅启动 PostgreSQL。首次初始化按现有 SQL 建立角色。BB-B2 分权卷先按生产部署契约补齐人员角色。数据库升级前先备份并停掉旧 API。
- `migrate` 使用已验证的 API 镜像 ID 和一次性迁移 DSN。确认迁移和获批的身份维护完成后再执行 `up`。
- `up` 复核快照与镜像，确认挂载源存在，并确认 PostgreSQL 已在运行且健康（不存在或不健康即拒绝，首次安装须先执行 `db`），然后只对 `baobei-api baobei-web` 执行 `--no-build --pull never --no-deps --wait`。新 release 目录会改变数据库初始化 SQL 的绑定挂载路径，若协调整个项目会重建 PostgreSQL；因此 `up` 与 `rollback` 都不协调数据库，并在切换前后核对 PostgreSQL 容器 ID 与启动时间不变。Web 的就绪检查覆盖 API 与数据库。再次核对运行容器镜像 ID 后，才更新生效指针。域名 HTTP-01 路径可达后，再按既有证书流程签发证书。

## 失败恢复

`pending.json` 记录进入部署阶段的提交。排查挂载、镜像、数据库或健康检查后，可重试同一 SHA。若有已生效的上一版本，且数据库迁移、初始化及授权契约哈希一致，使用本次失败或需撤回的 SHA 执行 `baobei_direct rollback`。入口以旧快照和核验过的本地镜像恢复，服务就绪后更新状态。流程保留数据卷。

首次部署的回滚目标为空。数据库契约变化时，直接回滚拒绝执行，负责人按备份恢复约定审核数据库恢复方案。旧镜像已被清理或快照缺失时，先恢复受审计的部署材料。操作者异常退出留下 `.lock` 时，确认无相关部署进程后清理该空锁目录，再继续同一 pending SHA。
