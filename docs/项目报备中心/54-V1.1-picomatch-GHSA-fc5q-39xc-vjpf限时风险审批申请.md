## 2. 漏洞与根因（VULNERABILITY_ROOT_CAUSE）

- 编号：GHSA-fc5q-39xc-vjpf / CVE-2026-112366，CWE-1333（正则表达式拒绝服务，ReDoS），CVSS 3.1 7.5（AV:N/AC:L/PR:N/UI:N/A:H），CVSS 4 8.7。
- 受影响版本：picomatch `<= 4.0.7`；**Patched versions: None**（GitHub Advisory 于 2026-11-17 复核）。
- 原理：picomatch 的 `analyzeRepeatedExtglob`（lib/parse.js）不检查**单分支**的重复 extglob，例如 `+(*)`、`+(*a)`。这类模式会编译成会发生指数回溯的正则，攻击者只要能**同时控制 glob 模式和被匹配的字符串**，就能阻塞 Node 事件循环。
- 本地实测：用仓库锁定的 picomatch 4.0.7 执行 `isMatch('a'.repeat(n)+'!', '+(*a)')`，n=18、22、24 时分别耗时 8、20、80 ms，耗时随 n 指数增长，漏洞属实。

## 5. 构建期风险（BUILD_TIME_RISK）：低，但不为零

picomatch 只在开发和构建工具里执行，具体有以下几处，每一处的 glob 模式都来自**仓库内经过审查的文件**：

- **Vite 构建/开发服务器**：模式来自 vite.config.ts 和插件，本项目只有 `@vitejs/plugin-vue`，没有使用 `import.meta.glob`。
- **Vitest**：模式来自它的 include/exclude 配置（默认值或仓库配置）。
- **vue-tsc / @vue/language-core**：模式来自 `vueCompilerOptions.dataAttributes/htmlAttributes`，tsconfig 中没有配置这两项。
- **typescript-eslint / tinyglobby**：模式来自 tsconfig 的 include（`src/**/*.ts`、`src/**/*.vue`、`vite.config.ts`）和 eslint.config 的 files/ignores。

仓库中这些配置都不含 `+(`、`*(`、`@(`、`?(`、`!(` 这类 extglob 写法。

**CI 能否从外部注入模式：** baobei-ci.yml 只由 `push` 到 `product/baobei-*` 和 `workflow_dispatch`（无 inputs）触发，没有 `pull_request` 或 `pull_request_target`，也不读取 `github.event` 中的任何字段。要改变这些模式，只能往受保护的产品分支推送提交，而这本来就要经过 OWNER 手动推送和审查。最坏情况是：有恶意提交写入一个恶意 glob，导致构建或测试卡住（只影响可用性，不影响机密性和完整性），而一个有权推送的人本来就能用更直接的方式做到同样的事。

**构建与生产隔离：**
- CI 在 GitHub 托管的一次性 runner 上运行；`baobei-build` 产出的镜像只包含 dist。
- 服务器 direct-deploy 在多阶段构建中执行 `npm ci --ignore-scripts`；`export_source` 只从 Git 对象中按白名单提取构建输入，构建上下文只有 package*.json、index.html、tsconfig、vite.config.ts 和 src/**。
- 构建容器不挂载任何运行凭据，生产的 web 和 api 容器里也没有构建工具。
