## 1. G3-2A 补充反证

**A. 隐藏候选处理状态（`TestDatabaseG32BHiddenCandidateStates`）。** 本组主管对主项目没有任何可读待裁决候选，只有一个跨组隐藏候选。全部状态都通过真实 API 制造：隐藏候选已提交待审、隐藏候选被总监批准、主项目被退回后再提交（第二轮重新识别隐藏候选）、另一个不在本轮的隐藏候选提交后被拒绝。每一步比较主管视角的 `review`（含 `eligible`、`reasonCode`、`pendingDuplicates`、`nextAction`）、`actions.approve/return/reject/duplicate-decisions`、`kind=pending` 与 `kind=duplicates` 列表中的成员与提示、首页 `reviewable` 与 `reviewQueue`。五个状态的整段 JSON 完全相同：`eligible=false`、`reasonCode=REVIEW_RELATED_PROJECT_RESTRICTED`、`pendingDuplicates=0`、`approve=DUPLICATE_DECISION_REQUIRED`；主管直接 POST 批准返回 409。同组无候选的对照项目可审，说明唯一披露的是“本项目当前由你无法完成”。

“历史裁决和本轮裁决并存”在真实状态机中不可达：任何重复裁决都会把主项目推进到 APPROVED（不是重复）或 REJECTED（确认重复）；APPROVED 不能退回；确认重复后不能再提交（`DUPLICATE_ALREADY_CONFIRMED`）；退回只发生在待裁决阶段。因此仍处于 SUBMITTED/UNDER_REVIEW 的项目不会带有已裁决 case。测试用真实 API 验证确认重复后再提交与退回均为 409，并对整库断言不变量 `in-review-with-decided-case=0`，没有通过改库伪造该组合。

**B. 未归一化原文断言（`TestDatabaseG32APrivacy` 扩充）。** 在四个变体中收集隐藏候选的实际项目 ID、报备编号、case ID、客户、省、市、厂区、设备类型、销售阶段（与可见项目不同的取值）、唯一需求文本、唯一预计采购日期，以及候选自身 `created_at` / `updated_at` 的 UTC、本地与微秒格式，共 88 个标记；在主管与销售五个入口的原始响应中逐字查找，均未出现。case 行自身的 `created_at` 是主项目提交事务的时间（主项目可见），不作为秘密。该断言在 G3-2A 前的 `8caed95` 上失败（主管对比原文含隐藏 case ID），在 `07215c9` 上通过。

## 3. 新 GET 契约（OpenAPI 1.3.0-g32b）

`GET /api/v1/reviews?kind=pending&eligibility=reviewable|blocked|all&page=1&pageSize=20`

| 参数 | 规则 |
| --- | --- |
| `eligibility` | `reviewable`：可执行下一项必要审核动作；`blocked`：范围内待审但不能执行；`all`：范围内全部待审。未传时保持原接口（只返回 `items`、`total`，`kind` 语义不变） |
| `kind` | 与 `eligibility` 同用时只能为 `pending` 或省略；`duplicates`、`protection` 与之组合返回 400 `INVALID_FILTER` |
| `page` | 正整数，默认 1；非法 400 |
| `pageSize` | 1–100，默认 20；越界 400（只在传入 `eligibility` 时生效） |
| 角色 | 销售 403（任何形式）；主管本组；总监授权范围；管理员全局 |

响应：

```json
{ "items": [Project], "total": 3, "asOf": "<服务端事务时间 UTC>", "counts": { "reviewable": 3, "blocked": 7, "all": 10 } }
```

`total` 等于 `counts[eligibility]`。每项新增 `submittedAt`（当前提交轮次冻结提交记录的时间，只在队列返回）与 `review.nextAction`（`approve` 或 `duplicate-decisions`）。

## 4. 审核资格 SQL 与权限范围

- 成员资格直接使用 `reviewableSQL("p")`；范围使用 `projectScope("p")`；待审定义为 `intake_status IN ('SUBMITTED','UNDER_REVIEW')` 且角色为主管/总监/管理员。首页 `workspace-summary` 的 `reviewable`、`reviewQueue` 用同一谓词。
- `reviewableSQL` 的待裁决计数 `pendingCasesSQL` 包含不可读候选，因此不会因为 `pendingDuplicates` 只计可读候选而误判“已无待裁决事项”；存在不可读候选时 `relatedCandidates` 判为受限，项目落入 `blocked`。
- `blocked` 的原因只来自服务端固定原因码：`REVIEW_CONFLICT`、`REVIEW_EVIDENCE_INCOMPLETE`、`REVIEW_RELATED_PROJECT_RESTRICTED`、`DUPLICATE_DECISION_REQUIRED`、`BUSINESS_PERMISSION_DENIED`、`INVALID_STATE`；不含不可读候选的属性或数量。
- 过滤、排序、分页都在数据库完成：`ORDER BY submitted_at ASC NULLS LAST, p.id`，`LIMIT/OFFSET`。ID 是最终稳定键。
- 快照：一个只读 `REPEATABLE READ` 事务内依次执行计数、取页、批量提示，`asOf` 为该事务的 `now()`。同一响应内 `items`、`total`、`counts` 与每项 `actions` 互相一致。首页与列表是两次独立请求，中间的真实业务变更会造成差异；一致性在相同数据状态下验证。
- 审核 POST 事务不变：版本、`reviewIndependence`、`candidateIndependence`、冻结证据、待裁决检查、历史证据确认与审计照旧；列表资格只用于展示与过滤。

## 5. 真实测试

**十项矩阵（`ten-item-matrix-four-roles`）。** 同组 10 条待审：3 条可审；4 条主管经手（提交前转交、提交后转交、两次转交、主管转交后总监再转交）；2 条存在跨组候选；1 条当前证据不完整。另一组另有 2 条隐藏候选。

| 角色 | reviewable | blocked | all | 说明 |
| --- | --- | --- | --- | --- |
| 本组主管 | 3 | 7 | 10 | 首页 reviewable=3、reviewQueue=10 |
| 总监 | 10 | 2 | 12 | 2 条为总监经手（总监转交过的“参与四”、证据不完整） |
| 管理员 | 11 | 1 | 12 | 仅证据不完整 |
| 另一组主管 | 2 | 0 | 2 | 只读本组 |
| 销售 | 403 | 403 | 403 | 任何 eligibility 均 403 |

主管 blocked 原因：4 条 `REVIEW_CONFLICT`，2 条 `REVIEW_RELATED_PROJECT_RESTRICTED`，1 条 `REVIEW_EVIDENCE_INCOMPLETE`。每项成员资格等于下一项必要动作的 `actions` 提示；reviewable 与 blocked 无交集且并集等于 all；主管队列原文不含隐藏候选的 ID 与报备编号。随后对 7 条 blocked 发 POST 全部被拒，3 条 reviewable 批准成功，队列与首页同步变为 0/7/7。

**参数（`parameters-and-legacy-default`）。** 不传 `eligibility` 时响应只有 `items`、`total`；6 种非法组合（duplicates/protection + eligibility、未知 eligibility、pageSize 0/101、page 0）均 400。

**1001 条分页（`pagination-1001-stable-ties`）。** 1 条经 API 提交，再复制其冻结提交 1000 次，所有提交时间相同，制造最坏并列。reviewable/100、all/20、all/9 三种分页逐页取到末页之后：末页条数正确（1、1、2），末页之后为空页，跨页无重复、无遗漏（1001/1001），提交时间单调不减；首页 reviewable=1001。

**并发（`stale-list-post-rejected` + 浏览器）。** 列表加载后总监先退回该项目，主管按缓存中可用的按钮批准：409 `VERSION_CONFLICT`，项目保持 RETURNED，刷新后的队列不再包含它。浏览器中冲突原因显示在确认对话框内，输入的审核原因保留，队列自动刷新。

**查询次数（`constant-query-count`）。** 60 条待审，pageSize 5 与 50 的数据库往返都是 5 次（事务开始、计数、取页、负责人团队、批量审核事实），与卡片数量无关。本机沙箱耗时约 4.8 ms / 11.9 ms（含 race 检测，仅作量级参考）。

**桌面/手机浏览器（`g32b-queue.spec.ts`）。** 首页“你可独立审核”与 `workspace-summary.reviewable` 一致，点击进入 `/reviews?eligibility=reviewable`；三个视图计数与首页一致；卡片显示项目名称、编号、报备状态、等待时长（只用 `submittedAt`）、下一步、是否可审及固定原因；“需要其他人处理”视图显示“你参与过此项目，需由其他独立审核人处理”；390 px 无横向滚动；过期按钮场景如上。截图仅保存在被忽略的 `local-private/baobei/g32b-evidence/`。

## 9. 遗留问题与 G3-2C 交接

1. 重复对比 `comparison()` 仍为 1+2N 次查询（G3-0 基线：50 候选 101 次），属 G3-2C，本批未改。
2. P2：报备向导只在客户、项目名称、省市、厂区、车间、招标号变化时实时查重；设备与需求变化不会触发，而服务端评分包含这两项。提交时服务端会再次查重，不影响门禁，留待后续批次。
3. 历史迁移数据没有冻结提交记录时 `submittedAt` 为空，等待时长显示“提交时间未记录”，排在队列末尾。
4. 首页与队列是两次请求，并发变更时数字可能短暂不同；队列内部为单一快照。
5. `blocked` 中“需要其他人处理”只说明原因，不指出具体由谁处理；按角色路由属后续工作台设计。
