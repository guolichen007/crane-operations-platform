# 41 · G4-S5-R1-E 身份迁移与管理员账号闭环验收

基线 `7dbbf63`（R0，Run 43011138383 8/8）。本批只交付代码与隔离验证；生产 Keycloak、生产数据库与服务器均未改动（PRODUCTION_MUTATION=NONE）。

## 1. 模型决定：业务 subject 不变，新 Realm 用确定性新 UUID + identity_links

在真实 Keycloak 26.8.1 上验证：用户 ID 在**整个 Keycloak 服务器**内唯一（`USER_ENTITY.ID` 主键）。只要共享 Realm `crane` 里的旧账号还在，同一 UUID 不能导入独立 Realm `baobei`（partialImport 409，OVERWRITE 同样失败，且本方案禁止 OVERWRITE）。

负责人确认现有测试账号可丢弃、投入使用前统一清理并正式新建。据此选用：

- 新 Realm 用户 ID = UUIDv5(业务 subject)，确定性、可重复计算；用户属性 `baobei_subject` 记录原业务 subject。
- 数据库新表 `identity_links(issuer, external_subject → subject)` 把新 Realm 的 `sub` 映射回原业务 subject。项目、审批、审计、参与记录中的 subject **一律不改**；`staff_subject_guard` 触发器使已绑定 subject 不可变。
- 共享 Realm 继续以 `sub = subject` 直接匹配，因此回切不需要改任何业务数据。

`UUID_PRESERVATION` 的含义因此是"业务 UUID 保留（经 links 映射）"，不是"Keycloak 用户 UUID 复用"。

## 2. Issuer 与会话隔离（A/B）

- 迁移 `00006_identity_realm.sql`（不改 00001–00005）：`identity_epoch` 单行（当前受信 issuer + 纪元号）；`app_sessions` 增加 `issuer`、`identity_epoch`，旧会话回填 `legacy:unknown/0`，永远无效。
- 会话只在 issuer 与纪元都匹配时有效；API 启动时若数据库信任的 issuer 与配置不同则拒绝启动（fail closed）。
- 切换只能用维护角色执行：`baobei-api maintenance identity-switch --realm <批准的 Realm> --operator <工号> --reason <原因> --takeover-admin <staff_id> --approval <接管方案编号> [--dry-run]`（G5-RC0 起：预检失败关闭、必须有可登录的接管管理员，见 45 号）。切换会删除全部 `app_sessions` / `staff_sessions` 并递增纪元；切回同样执行一次，旧 Cookie 在两个方向都失效。
- Realm 只能在部署档案的固定白名单中选择（生产：`baobei`、`crane`；Preview：`baobei-preview`），由 `BAOBEI_IDENTITY_REALM` 指定，不接受任意 issuer。生产默认仍为 `crane`；`compose.realm-baobei.yaml` 叠加文件切到 `baobei` 并挂载账号服务密钥文件。Crane 侧配置未改。

## 3. 账号服务（E）

- API 内的 Keycloak 适配层只用 `baobei-account-service` 客户端凭据，只访问 `baobei` Realm（Realm 与客户端固定白名单），只持有 manage-users/view-users/query-users/view-clients/query-clients，且同时写入客户端 scope mappings（`fullScopeAllowed=false`）。不使用 master Realm，浏览器不接触 Admin API 与凭据。
- 管理员网页操作：开通、重置密码、更换登录手机号、停用、恢复、任命角色，均有审计，审计不含密码。
- 开通顺序：先建**停用**用户 → 设临时密码 → 绑定唯一角色 → 写 link → 启用。任一步失败即补偿（删除新建用户 / 还原用户名 / 保持停用并标记 PROVISION_FAILED），不会留下可登录的错误权限账号。
- 临时密码由服务端一次性生成、只在本次响应中返回、从不入库；首次登录强制修改（UPDATE_PASSWORD）。管理员无法查看员工现有密码。
- 幂等：`Idempotency-Key` 唯一；每名成员同时只能有一个进行中的操作（部分唯一索引）；Keycloak 调用在数据库事务之外。
- 登录名 = 11 位手机号；`+86…` 不是同一登录名；员工不能自行改用户名（user profile 仅 admin 可编辑）。
- 每次登录 `prompt=login`；敏感操作重新认证 `max_age=0`；员工改密走 Keycloak `UPDATE_PASSWORD`（先验当前密码）。

## 4. 逐用户名单与最小导入（C/D）——由服务器 CC 执行

工具：`deploy/baobei/identity-migration.py`，只读、不读写任何密钥，输出手机号一律打码。

1. 导出（只读）：Baobei `app_users` 与引用计数（项目、创建、审批、参与、审计、跟进）为 JSON；`kcadm.sh get users -r crane` 及其 baobei-web 角色映射为 JSON。
2. `roster --app-users … --keycloak-users …`：逐行分类（IMPORT / IMPORT_BLOCKED 缺手机号 / 停用 / 归档保留历史 / 未绑定 / 合成账号 / 旧 Realm 无此 UUID / 角色不一致），并列出"仅在 Keycloak 有 Baobei 角色"的账号。这解释"9 个与 10 个"之类的差异：两侧口径不同（合成账号、未绑定成员、仅存在于 Keycloak 的账号），不得自动补齐或猜测手机号。
3. 负责人在计划中逐行标 `approved`。
4. `import --plan … --phones …`：只生成已批准行；用户全部停用、无凭据、无会话、仅 baobei-web 单一角色、无 Crane 组，`ifResourceExists=SKIP`。
5. `verify`：比对 Realm 实际状态与计划；`links --issuer …`：输出 identity_links 行，在 verify 通过后由操作员受控写入。
6. 由于账号可丢弃，推荐路径是：只迁移有历史引用的成员的 link，其余在新 Realm 由管理员网页重新开户。

本批未在生产运行 roster：`USER_ROSTER_RECONCILED=NOT_RUN`。
