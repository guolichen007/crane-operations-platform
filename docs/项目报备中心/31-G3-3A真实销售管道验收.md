## 1. 阶段数据字典

`sales_stage`（销售阶段）与 `intake_status`（报备审核状态）是两个独立维度；`next_followup_at` 是真实下一次跟进时间；`updated_at` 只是数据更新时间。管道按 `sales_stage` 分栏，卡片上的“报备：…”标签是 `intake_status`。

| 顺序 | 编码 | 中文 | 说明 |
| --- | --- | --- | --- |
| 1 | `L0_LEAD` | 线索 | |
| 2 | `L1_REQUIREMENT` | 需求确认 | HOLD 唯一的恢复目标 |
| 3 | `L2_TECHNICAL` | 技术交流 | |
| 4 | `L3_SITE_SURVEY` | 现场勘察 | |
| 5 | `L4_SOLUTION` | 方案 | |
| 6 | `L5_QUOTATION` | 报价 | |
| 7 | `L6_TENDER` | 招投标 | |
| 8 | `L7_COMMERCIAL` | 商务沟通 | |
| 9 | `L8_PENDING_CONTRACT` | 待签约 | 不代表报备已批准 |
| 10 | `WON` | 已成交 | 只能从待签约进入，进入后不可再变 |
| 11 | `LOST` | 已失单 | 需原因，进入后不可再变 |
| 12 | `HOLD` | 暂缓 | 需原因，只能回到需求确认 |

“已批准”（`APPROVED`）只是报备状态，不是阶段；任何阶段都可以处于任何合法报备状态（测试：同一 L3 栏同时有草稿、已提交、退回、已批准）。

## 2. 接口契约（OpenAPI 1.4.0-g33a）

**新增 `GET /api/v1/stage-summary`**

```json
{ "asOf": "<UTC>", "scope": "OWN|TEAM|ALL_ASSIGNED|ALL", "filters": {"province": "江苏省"},
  "total": 123, "stages": [{"code": "L0_LEAD", "count": 12}, … 共 12 项], "unclassified": 0 }
```

- 范围：直接复用 `projectScope`（与 `/projects`、首页同一谓词）；默认包含范围内全部报备状态。
- 基础筛选 `q`、`status`、`province`、`updatedAfter`，与 `/projects` 同义，作用于全部阶段。`stage`、`page`、`pageSize`、`sort`、`followup`、`assignment`、未知参数、重复参数、非法枚举一律 400 `INVALID_FILTER`。阶段选择不会改变其他栏的统计口径。
- 计算：一条 `SELECT p.sales_stage, count(*) … GROUP BY p.sales_stage`，不在 Go 中加载项目。
- `stages` 固定 12 项、固定顺序，数量为 0 的阶段也返回。`unclassified` 为库中 `sales_stage` 不属于 12 个标准编码的项目数（数据质量提示），恒有 `sum(stages)+unclassified = total`；不改写历史数据，页面在 `unclassified > 0` 时显示提示。
- 不返回任何金额字段（G3-3B）。

**`GET /api/v1/projects` 的最小兼容收紧**

- `stage` 已在白名单中（非法阶段原本就 400），OpenAPI 补充 12 值枚举。
- `page`（1–1,000,000）、`pageSize`（1–100）此前非法值会静默回落为默认值，现在 400 `INVALID_FILTER`；现有前端与测试调用均为合法值。旧 `/reviews` 不带 eligibility 的固定 20 条不受影响。
- 过滤条件构造抽成 `projectFilters()`，`/projects` 与 `/stage-summary` 共用同一段代码（同一 `projectScope`、同一筛选 SQL），排序仍为 `updated_at DESC, id`，以 ID 打破并列。

## 5. 阶段推进（`stage-transition-moves-counts-and-keeps-rules` + 浏览器）

后端（现有 `stage-change` 接口，未改）：越级（L1→L4）409、缺原因 400、主管/总监直接 POST 403、旧版本 409、未到待签约直接成交 409；以上均无审计写入、计数不变。合法推进 L1→L2 后报备状态仍为 SUBMITTED，L1 −1、L2 +1，审计恰 1 条且含 `fromStage`/`toStage`；同一旧请求重放 409，不产生第二次变更。HOLD 只能回 L1（越级恢复 409），LOST 后不能再改。

浏览器（4 个视口各一遍）：卡片“推进阶段”先读取最新项目，弹窗只列合法目标（技术交流 → 现场勘察 / 暂缓 / 已失单，与服务端规则镜像，Vitest 覆盖）；未选目标或无原因时确认按钮禁用。另一会话先更新项目后确认：弹窗内提示“项目已被其他人更新”，原因保留，卡片仍在原栏，弹窗已重新读取最新版本；再次确认成功，原栏 −1、新栏 +1，审计 1 条。没有拖拽改阶段。

## 8. PG18 规模实测

环境：生产镜像 `postgres:18.4-alpine`（固定 digest）二进制、默认 JIT；数据为第 29/30 号同一生成器（1 个 API 种子 + N 条合成克隆，按漏斗形态分布到 12 个阶段）；`pg_stat_statements` 读取应用实际执行语句的 JIT 计时；冷 = 重启清空 shared_buffers 后首个请求。查询数含会话校验。

| 10k | 视角 | 查询数 | 冷首请求 | 热 P50 / P95 | JIT 函数 | 响应字节 |
| --- | --- | --- | --- | --- | --- | --- |
| stage-summary | 主管 / 总监 / 管理员 / 销售 | 2 | 21–23 ms | 2.4–3.1 / 2.7–3.8 ms | 0 | ~520 |
| stage-summary（省份+状态筛选） | 四角色 | 2 | — | 3.0–3.1 / 3.3–3.6 ms | 0 | ~560 |
| 单栏第 1 页（10 条，栏内 477–1,432 项） | 四角色 | 4–5 | 25–34 ms | 3.8–6.9 / 4.2–7.7 ms | 0 | ~25 KB |
| 单栏末页 | 四角色 | 3–4 | — | 6.8–11.7 / 8.0–12.0 ms | 0 | 5–17 KB |

1k：stage-summary 热 P50 0.5–0.6 ms；单栏第 1 页 1.7–3.1 ms、末页 1.8–3.0 ms；JIT 均为 0。

执行计划（10k，总监）：统计为 `Seq Scan intake_projects → HashAggregate`，12 组，shared hit 4,061，执行 2.2 ms；单栏计数与取页为同表顺扫 + `Sort (updated_at DESC, id) top-N heapsort`，执行 1.8 ms 与 2.7 ms。估算代价约 4,200，远低于 `jit_above_cost=100000`，不触发 JIT，因此本批没有使用 G3-3-P0 的事务内关闭 JIT。全表顺扫在 10k 时只有约 4,000 个缓冲页，随规模线性增长；若后续数据量明显增大，可考虑 `(sales_stage, updated_at DESC, id)` 索引（需新迁移，本批未加）。完整计划与原始行：`local-private/baobei/g33a/jit-g33a.md`、`prog-g33a.txt`。

## 11. 遗留问题与 G3-3B 交接

1. 管道卡片暂不显示金额；G3-3B 前须先核实 `estimatedAmount` 的真实写入、`knowledge` 标记（KNOWN/UNKNOWN/LEGACY_UNCONFIRMED）与历史迁移语义，再以 numeric 聚合、十进制字符串返回已知金额与未知数量；不得把未知显示为 0，不得把 LEGACY_UNCONFIRMED 计入可信金额。
2. 筛选尚无负责人、团队、城市；14 号 PRD 列出的这些筛选留待后续批次。
3. 统计与各栏是独立请求，并发变更时可能短暂不一致；已提示并可刷新，未实现跨请求快照。
4. 规模增大后阶段栏的顺扫与排序可考虑复合索引（新迁移，需单独评审）。
5. 第 29/30 号登记的事项仍未处理：`blocked` 文案；队列未知参数静默忽略；向导设备/需求变化后不重新查重；实时查重线性扫描；四角色高保真工作台；历史设计文档中过时的描述。本批复用的分页组件没有“加载失败时旧总数驱动分页”的问题（各栏只在成功响应后写入 total，失败态不显示“加载更多”）。
